## 2026-08-19（夜）· 自己编求解器：拦路虎少了一个，EV 那一个还在

用户在三条路里选了「从源码编译、直接向求解器要 EV」。先做可行性，别一头扎进去写 C++。
**一段做完，结论比预想的好**（完整实测表见 ADR-0006）：

- **编得出来**：官方有专门的 `console` 分支（CMake，就是我们手上那个预编译包的来源），
  **不需要 Qt**，依赖全在 `ext/` 里随分支发。本机 2 核 3.6 GB `make -j1` 编得动。
  别照 master 分支编——那是 Qt 的 GUI 工程。
- **原地换得掉**：同一份命令文件，新旧二进制 dump 出来的动作标签逐字相同；
  三项求解慢测在新二进制上全绿。
- **意外收获：具体组合喂得进去了**。console 分支的范围解析器有 `range_len == 4` 分支，
  实测 `set_range_ip AhKs,QdQc,7h6h` 正常求解、dump 里 `AhKh` 独立成条。
  **我们记了很久的「范围只认 169 个牌类」是版本差异，不是格式限制**——
  方案 B「同花听牌被抹平」那个保真度上限，原则上可以拿掉。
  代价：范围里一出现具体组合，它自动关掉花色同构（会打印警告），**慢多少还没量**，
  所以先不默认打开。
- **EV 还是得自己加**：dump 里依然没有 EV。但 `PCfrSolver::actionUtility` 里
  `all_action_utility[action_id][hand_id]` 就是逐动作逐手牌的收益，**本来就在算，只是没往外吐**。
  下一段给 console 加一条 `dump_evs` 命令把它吐出来。

**传输方式改了个形式**：不走 ctypes FFI，走「给 console 加一条命令」。实质一样
（都是从源码编译、直接问 EV），但 `backend.py` 仍是全项目唯一碰进程与磁盘的地方，
指纹缓存照用，Windows 那台也只是照样编一次。要问的线路在求解之前就全知道
（`plan_review` 先出计划再求解），所以一次进程跑完「求解 + 全部查询」不吃亏。
理由与代价写进 ADR-0006，构建步骤写进 `docs/solver-build/`。

### 顺手抓到一条从 FR-9 起就错的慢测

跑求解慢测时炸出 `KeyError: 这个决策点上没有「BET 3.000000」`。查下来**与新二进制无关，
旧二进制一样炸**：`SolvedAction.label` 是树里的原始键（求解器单位，1/10 大盲），
`.amount` 才是大盲，所以 3.0bb 那一注在树里叫 `BET 30.000000`。
生产路径没问题（`review._match` 按「动作类型 + 大盲金额」找，再取它的 label），
**是那条慢测写死了标签字面量**，而慢测默认不跑，于是从 FR-9 一路绿到今天。
教训进 CLAUDE.md：**别手写标签字面量**。

## 2026-08-19（晚）· FR-10 Windows 真跑：纯逻辑全过，真解撞在「方案 A 还没拆掉」上

Windows（7.8 GB 内存）把清单里能验的都验了。**三项通过 + 全量回归全绿；两项真解没做成**——
而没做成的原因不是机器小，是**代码还在按方案 A 跑**，下面第三节。

### 通过的

| 项 | 结果 |
|---|---|
| 第 1 步 冒烟 `--hands 300 --plan-only` | 可复盘 32 手（11%），105 个待打分决策点 |
| 　→ 文案回归 | 「翻前就结束了，没有翻后决策」99 手**单独一格**，与「翻牌时还有 3 个人」分开了 ✅ |
| 第 4 步 短筹码 `--stack 20 --hands 400` | 可复盘 0 手，与 Linux 一致 → 确认是筹码深度的必然，不是 `range_tracking` 漏判 |
| 全量回归 | Windows 上 462+12 项全绿（含 FR-10 的 12 项新测试） |

### 内存轨迹（这是这轮最有用的产出）

| 局面 | 参数 | 峰值 | 结果 |
|---|---|---|---|
| 真实规模抽样（OOP 472 / IP 1130 组合，97.5bb，dump3） | iter20/thr4 | 3.65 GB+ | 219s 未收敛，可用内存见底停手 |
| 同上 | iter10/thr2 | 4.55 GB | 144s 未收敛 |
| 小局面（双方各 3 牌类，97.5bb，dump3） | iter10 | 3.64 GB | 289s，dump 阶段被停 |

**求解迭代阶段内存涨得很慢（小局面才 ~415 MB），dump 阶段 30 秒内 415 MB → 3.6 GB。**
爆的是导出、不是求解——与 pilot 那条「产物大小只由 dump 层数决定」完全对得上，
这次是从内存侧又验了一遍。**双方各 3 个牌类、97.5bb 就要 3.6 GB**，真实范围必然 10 GB 级。

### 结论要纠正：不是「该换 16 GB 的机器」

Windows 那边的结论是「FR-10 成规模跑需要 ≥16 GB」。**方向反了**：dump3 层就是**方案 A**，
而方案 A 在 2026-08-19 上午的 pilot 里已经判了死刑（见上一条 DEVLOG 与 ADR-0005）。
真正的原因是 `review.plan_review` 里还硬写着 `request_options.setdefault("dump_rounds", 3)`——
`rollout.py`（方案 B 的接缝）写完了、14 项测试绿了，**但一行都还没接进 `review.py`**。
所以这次 Windows 跑的仍然是方案 A，撞墙撞得完全符合预期。

**换 16 GB 机器解决不了问题**：pilot 已经量到，那条路上一个局面 10 GB 级产物 + 远不收敛，
`--max-solves 20` 是几十 GB 与十几小时。**要拆的是代码，不是买内存。**

### 但方案 B 有个此前没算到的洞：它给不了**翻牌**决策的 EV

接线之前先把账算清楚了，免得接完才发现：

- EV 是**把后面的期望积出来**的（dump 里没有 EV，只能自己在树上走）。所以给一个**翻牌**
  决策打分，需要翻/转/河三层都在树里——那正是 dump3＝方案 A。
- 方案 B 每街一棵 dump1 的小树：翻牌树里任何一条走到转牌的路都没有下文，
  `evaluate.py` 会照实抛「发牌节点下面是空的：dump 的层数不够」，那个点被跳过。
- **能算的是**：河牌决策（河牌树 dump1 本来就是完整的）、转牌决策（从转牌起树 dump2＝转+河，
  比翻牌起 dump3 小一个数量级）。
- **翻牌决策要算，只有三条路**，都不便宜：整树 dump3（方案 A，大内存机）／对每个动作抽样
  若干张转牌各解一棵（一个翻牌决策要几十次求解）／从 AGPL 源码编译 C FFI 直接问 EV（不 dump）。

翻牌决策占决策点的大头，所以这不是边角——**FR-10 的形状取决于选哪条**。已列成岔路待拍板。

### 交叉验证的锚点要跟着改

DEVLOG 上一条留的「同一局面：A 整树 vs B 逐街，EV 损失对得上吗」，**锚点从翻牌决策改成
转牌决策**：翻牌决策在 B 里根本算不出数，对不了；转牌决策两边都出得来数，
而且验的正是 B 唯一新增的那道工序——**把上一街的解滚成下一街的范围**（`rollout.py`）。
20bb 小范围下 A 还跑得动（pilot：822.8 MB / 325s），**这仍然是唯一一次能做的独立验证**。

### 交付：漏洞报告现在自己说得清「这份排行可不可信」

顺着「可利用度那一栏值得看一眼」这条线查下去，发现**报告根本没带这一栏**：
`leak_report.py` 只把可利用度打在每次求解的进度行里，`build_report` 看不到、
`leaks.json` 里一个字都没有。一份事后交出去的 `leaks.json`，**没人判得出它可不可信**。

- `leaks.Convergence`：逐个解的可利用度、门槛、没量到的次数，并把可利用度折成大盲
  （`可利用度% × 底池`）——跟漏损同一把尺子才比得了。
- 第二路残差用**解自己在打分那几个点上的 `gap`**（`DecisionScore.gap`，我们在树上算的，
  不依赖日志）。噪声底两路**取大的**。表外牌不参与：解没给它频率，那里的 gap 是假的。
- `ranking_trustworthy()`：平均每点漏损要比噪声底大出 3 倍才算数；**量不到就返回「判不了」，
  不返回「通过」**。命令行与 `leaks.json` 都带上这一段。

**为什么这件事非做不可——把默认参数代进去算一遍**：`leak_report.py` 默认
`--iterations 60 --accuracy 1.0`，而 `accuracy 1.0` 是个够不着的门槛（pilot：97.5bb 跑到
20 迭代时可利用度还有 **59.5%**），所以真正管事的是 60 次迭代那个上限。
单次加注底池约 6 bb → 噪声底 ≈ **3.6 bb / 每个决策点**，而真实的单点 EV 损失是 0.05–0.5 bb 量级。
**信噪比 0.1 上下**：那份排行量的不是漏洞，是求解器的残差。更糟的是负差在合计里按 0 算
（`_loss_of`），噪声**只加不减**，于是排行会朝「出现次数最多的格子」倾斜——
看起来还挺像那么回事。60 次迭代离可用（0.5–1%）差**一到两个数量级**，
不是把 `--iterations` 调到 200 能补上的。

所以第 3 步就算在大内存机上跑成了，那份 `leaks.json` 也不能拿来指导改打法。
**先把收敛度量清楚，再谈排行。**

## 2026-08-19 · 求解粒度 pilot：方案 B（逐街分别解）胜出，但保真度有个上限

Windows 上跑完的 pilot 把 ADR-0005 留的拦路虎解掉了（完整数据表进了 ADR-0005 新增一节）：
**整树 dump 3 层的产物是 GB 级，判死刑；逐街分别解每棵 ~0.2 MB、分钟级，选它。**
成本的主导因素是**筹码深度**与 **dump 层数**，范围大小和下注尺度个数都不主导。

两条这轮新挖出来的、会改变下一段做法的事：

1. **pilot 的时间数字不能当可用解的价格**。它跑的是 20 迭代 / accuracy 1.0，
   可利用度还在 17%（20bb）到 59.5%（97.5bb），远没收敛；而且越深越不收敛，
   真实成本比「随深度线性」更陡。**要按真实精度重量一次**，见下面待验证。
2. **求解器的范围输入只认 169 个牌类，喂具体组合直接 abort**
   （`range str AhKs len not valid`，跟 `+` 记法同一类坑）。而解出来的策略是逐组合的——
   于是「从上一街的解滚出下一街范围」这一步**只能按牌类聚合，同花听牌会被抹平**。
   这是方案 B 的保真度上限，不是实现细节。预编译包没有 FFI 库（`.so`/`.h` 都没有），
   要逐组合喂回去得从源码编译，另算一笔账。

### 已交付：方案 B 第一段——滚范围（`holdem_solver/rollout.py`，14 项测试）

`roll_forward(root, prefix, request=…)` 沿实战走过的线把双方范围滚到下一街，
`Rollout.to_request(上一街的请求)` 直接造出下一街那棵树的请求（公共牌、底池、有效筹码
都推进好，跑法参数默认沿用）。三条口径：

- **权重＝输入权重 × 沿途每一步的动作频率**，逐组合各算各的；解里查不到的组合是
  「走不到这儿」直接删，**滚成 0 的组合要留着**——留着才看得出一个牌类里有没有哪支被
  单独摘出去（写这段时先按「掉到 0 就删」实现，结果同花听牌被摘走时类内落差反而算成 0，
  等于把损失藏了起来，改成保留零权重组合）。
- **聚合损失要出现在产物里**：每个牌类算「类内落差」`(最大−最小)/最大`，
  `flagged()` 点名落差超过 0.35 的类，接到 PRD 的 A/B/C 置信度分级上。
- **滚出来的范围只能说牌类**：有一条回归专门断言渲染出来的每个词都是 2–3 字符，
  免得哪天又把具体组合喂进去让求解器 abort。

下一段：把它接进 `review.py`，跑通「翻牌解 → 滚转牌范围 → 转牌解 → 打分」的闭环。

## 2026-08-18 · M3 第三段：把牌局接上——逐个翻后决策点打分（FR-9）

**交付**：`holdem/range_tracking.py`（从打完的牌回推翻牌时双方的范围，13 项测试）+
`holdem_solver/review.py`（牌局 → 待打分的决策点 → 逐点 EV 损失，18 项测试含 1 项真跑
慢测）+ 求解器格式的 2 项回归。**全量 462 项快测全绿。**
到这一段为止，「打完一手牌，问每个翻后决策亏了多少大盲」这条链路是通的：

```python
plan = plan_review(hand, hero_seat=3)   # 纯逻辑：解哪个局面、打分哪几个点
report = solver.solve(plan.request)     # 唯一碰进程与磁盘的一步
result = score_plan(plan, report.root)  # 纯逻辑：逐点 EV 损失
```

**范围不是猜的**。任何翻后求解的第一个输入都是双方范围，而**范围错了，后面每一个 EV
损失都是错的、还看不出来**。所以 `range_tracking` 只认表里真有的那几条线路——单次加注
底池、3bet 底池——其余（跛入、多人底池、4bet 之后、深度差一倍以外）一律抛 `NotCovered`
**并说清为什么**。这跟 `preflop_policy` 查不到就回 `None` 是同一条纪律。

**接线这一段，真正的活都在「说不了的时候怎么说」**：

1. **实战打出的尺度必须先并进树里**（`BetSizes.with_size`），否则那个动作在解里根本不
   存在，也就没法给它打分。350 打进 550 的底池是 63.6%，默认的 33/75 都不算「相近」
   （2 个百分点以内才算），得为它多长一层树。
2. **树里没有的尺度就说没有，不许四舍五入到最近的那个**。一个说不清来路的
   「你这手亏了 2.3bb」比没有数字更糟。
3. **一个点打不了分，不能让整手牌作废**：尺度对不上、dump 层数不够，都只影响那一个点，
   其余的照常出分（`ScoredDecision.skipped` 写明原因）。
4. **英雄的牌可能不在我们假设的范围里**——风格层本来就会打表外的牌。这不是错误：EV 照样
   算得出（英雄的牌是固定的），但解在那个点上没给这手牌频率，所以 `in_range` 标出来，
   聚合时别跟正常点混着平均。

**真跑一次就抓出三条「本地全绿」掩盖不住的口径问题**——两个都是**这一段接线之后
才可能暴露**的，因为在此之前没人拿「实战打出的那个尺度」去树里找过：

1. **`set_bet_sizes` 同一格发第二条命令是覆盖，不是追加**。我们给翻牌设了 33/63.6/75
   三个尺度、各发一条命令，**树里只剩最后那个 75%**，而且求解器一声不吭照样解完。
   复盘时的症状是「实战打的 3.5bb 树里没有，最近的只有 4.0bb」——差点被当成容差太严。
   多个尺度得写在同一行：`set_bet_sizes ip,flop,bet,33,63.6,75`。
2. **它把算出来的下注额取整到整数单位**。底池 5.5 打 33% 是 1.815，树里是 `BET 2.000000`
   ——**实际打出去的是 36.4% 而不是 33%**。金额可以是小数（`set_pot 5.5` 认），
   取整的是它自己算出来的下注额。于是命令文件里的单位改成 **1/10 大盲**
   （`SolveRequest.scale`，粒度 0.1bb），解回来时除回大盲，对外的字段一律还是大盲。
   实测确认：一条命令给 33/63.6/75，树里三个下注选项齐了。

第二条对 EV 的影响是实打实的：按 36.4% 的树去给一个 33% 的下注打分，尺度错了，
EV 损失也就错了——而这种错**看着完全正常**。

3. **翻牌复盘的 dump 必须导满三层**。原本默认 `dump_rounds=1`，想着「先给翻牌上的决策
   打分，够用就行」——真跑才发现**连翻牌上的决策都算不了**：EV 是把后面的期望积出来的，
   任何一条走到转牌的路在树里都没有下文。于是 `plan_review` 默认改成 3。
   代价是产物大、解得慢，但这一层本来就只服务复盘。

**端到端真跑的账**（引擎打一手 → 规划 → 真解 → 打分，双方各 3 个牌类、有效筹码 20bb、
翻牌三个尺度 + 全下、导满三层）：**产物 163.7 MB**、求解 156 秒（2 线程）、
**在树上给一个决策点打分 1.4 秒**。实战那一注（63.6% 底池）算出来的 EV 损失是 0.233bb，
最优是 33% 那一注——不过这次只跑了 11 轮、可利用度还有 25% 底池，**这个数字只说明链路通了，
不是可以拿去教人的结论**。

**由此看清了下一段真正的拦路虎**：产物大小随深度与范围爆炸。换成真实范围（几十个牌类）
与 97.5bb 深度就是 GB 量级——**「每手牌解一次完整翻牌树」这条路走不通**。
下一段先定复盘的求解粒度，候选三条：逐街分别解（转/河的范围要从上一街的解里滚出来）、
只解被问到的那个决策点所在的街、或者走 TexasSolver 的 C FFI 直接问 EV 而不 dump 整棵树。

**样本为什么用河牌局面**：这一层自己不算 EV、也不解牌，测试要盯的是接线。河牌局面胜负
确定，每条路的 EV 都能用纸笔核对（对手全是暗三条、英雄 KK：过牌 0、下注 3 白扔 3、
对手弃牌则赢下底池）。翻牌局面要枚举 45×44 种跑马，EV 就成了「算出来的数」而不是
「核得出的数」——接线对不对，该在胜负确定的样本上验。

## 2026-08-18 · M3 第二段：在解出来的树上算 EV

**交付**：`holdem_solver/evaluate.py` + 17 项测试。求解器不给 EV，这一层自己算：
**固定英雄的两张牌**，对手按解出来的策略走，在树上把期望积出来，得到每条路的 EV
与「你这一手亏了多少大盲」。FR-9 的地基由此齐了。

**验证不靠「看着像」，靠三道**：

1. **手算对账**。专门造了个河牌局面：OOP 全是暗三条、IP 全是一对，摊牌胜负完全确定。
   于是 IP 拿 AA 面对 3 的下注（底池 6）三条路的 EV 都能用纸笔算出来——
   **实测跟注 −3.0000、弃牌 −0.0000、全下 −9.0000，一分不差**。坚果那边同样：
   OOP 拿 QQ 每条路都正好值一个底池。
2. **口径硬约束**。弃牌的 EV 恒等于「−已经投进去的钱」。专门有一条测试走
   「下注 3 → 被加注到 9 → 弃牌」，那个数必须**正好是 −3**：金额是「本街投到多少」的
   总额，算增量时减错一次就会变成 −9 或 0，而两者都还「看着挺像」。
3. **与求解器互证**。按解的混合策略打 vs 挑最好的那条路，两者的差应当与求解器自己报的
   可利用度同一量级。河牌样本上实测：范围平均差 0.00005bb（OOP）与 0.02035bb（IP），
   求解器报的 0.170% 底池折合 0.0102bb——**同一量级**。我们的 EV 要是算错了，
   这个差会明显鼓起来，而不是停在千分之几个大盲。

**跨街这条路上踩的三个坑**，都是真产物才暴露得出来的：

1. **发牌节点的子节点在 `dealcards` 里，不是 `childrens`**（而且没有下划线）。
   我第一版读 `childrens`，看到「发牌节点没有子节点」，差点写下「跨街 EV 算不出来」这个
   结论——**全树一扫，发牌之后有 1920 个带策略的动作节点**。差一点就因为一个键名把
   整条路线判了死刑。教训：**下结论前先做一次全树统计，别信第一眼看到的那个节点**。
2. **`dealcards` 里有 52 张牌，包括牌面上已经有的**（子树是空占位符）。不过滤的话，
   期望里会混进根本发不出来的转牌。
3. **「发牌节点下面是空的」有两种**：双方（有效）全下 → 后面本来就没有决策，该我们自己
   把牌发完再摊牌；dump 层数不够 → 必须报错。判据折腾了两轮：`deal_number` 两种都是 0
   分不开；「投入 == 有效筹码」也不行——求解器的 `allin_threshold` 会把「加注到 27、
   身后还剩 3」也变成没有后续决策。最后用的是**同一层有没有别的发牌节点展开过**，
   这条判据从树自身取证，不依赖对求解器内部规则的猜测。

**性能比担心的好**：固定英雄的牌之后，每个摊牌终局只要把这一手与对手范围逐手比一次，
再**按最终牌面缓存比牌结果**（同一条跑马下的终局共用一份）。实测一个转牌局面
（双方各 4 类范围）算完全部动作的 EV **不到 0.1 秒**。真正贵的是翻牌局面的 45×44 跑马，
以及范围大到几百个组合时——那是几秒到几十秒的量级，复盘完全够用。

**下一段**：把牌局接上——从 `HandState` + 双方范围造出 `SolveRequest`，
再把每个翻后决策点喂给这一层。这一步的拦路虎不是求解，是**范围跟踪**
（翻牌时双方各自可能拿着什么），那是 FR-11 的活。


## 2026-08-18 · M3 起步：接 TexasSolver（后端换了、约束也变了）

**交付**：`src/holdem_solver`（`request` / `result` / `backend`）+ 35 项测试 + ADR-0005。
本机 Linux 上**真解通了**：命令文件 → 跑二进制 → 策略树 → 按指纹缓存，第二次直接命中。

**一上来就推翻了立项时拍板的后端**。设计方案写的是「TexasSolver **GPU** 版，CPU 作降级」，
实测发现 GPU 版是 **Windows-only、只有 GUI、闭源、EULA**，仓库明说 gpu_solver 源码不开源，
**没有任何 headless / 命令行 / API 求解接口**（只带一个看结果的 viewer）——自动流程里
根本用不了。能自动化的只有 AGPL 的 CPU 版，它有 console 命令行与 C FFI，跨平台，
本机拉下预编译包直接跑起来了。**「有 GPU 版」不等于「能调用 GPU 版」**，这跟 ADR-0002
那条教训（「公开了 checkpoint」不等于「可复用的强模型」）是同一个错的两次犯。

**三条格式坑，全是实测才知道的**（文档一个字没写）：

1. **范围不能用 `+` 记法**。`set_range_ip 99+` 会让求解器抛 `format not recognize` 然后
   **直接 SIGABRT**（退出码 134，不输出任何东西）。我们自己的记法里 `+` 到处都是，
   一不留神就原样送进去了——所以渲染层一律展开成逐个牌类，并且钉了一条测试。
2. **金额可以是小数**（`set_pot 12.5` 实测可用）。于是全程用**大盲**当单位，
   不必为了迁就求解器换算成整数筹码。
3. **它管 OOP 叫 player 1、IP 叫 player 0**。怎么验的：给 IP 只放 AA、OOP 放小对子，
   看根节点 `player=1` 里出现的是谁的牌——是小对子，所以 1 才是 OOP。
   **取错一侧的解看着仍然「像那么回事」**，这是本项目栽过的同一类跟头（子博弈里
   玩家 0 是防守者那条），所以读进来就翻译成我们的口径，并且有测试守着。

**三条把 M3 形状定死的约束**：

- **只解两人**。TexasSolver 是两人求解器 → 复盘打分只能覆盖「翻牌时只剩两个人」的手牌，
  多人底池一律标「不打分」，不许拿两人解去凑。
- **dump 里没有 EV**，只有策略（逐具体组合）。官方样例里 `ev` 字段一个都没有。
  所以 FR-9 的「EV 损失」得**我们自己在解出来的树上算**——终局收益 + 到达概率，
  与 `preflop_solver` 同一套办法，只是终局换成真实摊牌。**拿「你打了低频动作」冒充
  EV 损失是不诚实的**，不做。这是下一段的主要工作量。
- **一个局面几分钟**（本机双核：小树 20 迭代 48 秒，可利用度还有 4%；官方基准 6 线程
  172 秒到 0.275%）。所以**实战中现解不可行**，这一层只服务复盘；也所以**缓存是必需品**，
  按请求指纹存盘，跑法（线程数、输出路径）不进指纹。

**求解器不随包走**：AGPL-3.0，自用没问题、随包分发要同协议开源、做联网服务更不行。
所以我们只调用，路径由 `TEXAS_SOLVER_HOME` 给，没装就明确报错并给安装说明——
**绝不悄悄退回近似**（PRD 的「诚实」那条）。

**下一段（FR-9 的核心）**：在解出来的树上算 EV。要处理发牌节点（turn/river 的 45/44 张，
且 `set_use_isomorphism 1` 会把同构牌面折叠，算 EV 时可能得关掉）与真实摊牌评估
（`evaluator.py` 现成的）。这一段做完才谈得上「每个决策的 EV 损失」。


## 2026-08-18 · 单挑 200bb 范围表：让 FR-6 量的是解，不是兜底规则

**交付**：`preflop_ranges_hu_200bb.json`（**23 秒**生成，可利用度 **0.0008 大盲/手**）+
`preflop_policy` 按人数分发范围表 + 深度守卫。对 Slumbot 的翻前决策
**从 0% 变成 97.4% 照解走**（剩下的 2.6% 是 4bet 之后的局面）。

**单挑不走六人桌那套分解**。六人 62 万节点跑不动才拆成子博弈链式合成；单挑整树只有
几十个节点，**直接精确解**——自证方式也因此不同：六人桌那张看「范围还变不变」
（`max_change`），单挑这张看**可利用度**，那是自证的，比任何外部对照都硬。
产物 schema 是同一套，所以 `preflop_policy` 一行都不用改就能查。

解出来（200bb、开牌到 2.5bb、不含跛入）：

```
BTN 开牌 69.6%
  BB 应对：弃 26.7  跟 51.8  3bet 21.5
  BTN 面对 3bet：弃 33.4  跟 57.0  4bet 9.6
```

对照 Slumbot 实测：它按钮位开 **89.5%**、我们 69.6%；它大盲面对 2.5bb 开牌弃 **16.1%**、
我们 26.7%。**开牌那一项别急着当差距**：Slumbot 开的是 **2.0bb**（895 次全是这个尺度），
开得小自然开得宽；公开的单挑 2.5x 开牌范围本来就在七成上下，我们这个数是对得上的。
**大盲弃牌那一项才是真偏差**（26.7% vs 16.1%），与 A 档校准那次的发现一致
（单挑下我们大盲弃得更多），账仍挂在兑现模型上，等 B 档校准。
想要一张按 2.0bb 开牌的表，`--open-to 2.0` 重跑 23 秒就有。

**默认关掉跛入**，因为 Slumbot 实测 895 次首行动全是开牌、一次跛入都没有；带跛入的树
比「开牌频率」等于比两件不同的事（校准脚本也是这么处理的）。

**顺手挖出两个一直在悄悄生效的 bug**——都是「测试全绿但功能没通」那一类：

1. **「面对再加注」这一格从来没查通过**。表把开牌者的应对存在
   `defense(开牌者, 3bet 者).reraise_reply` 里，策略层却去查 `defense(我, 我)`——
   那个键永远不存在，于是这整行局面一直退回兜底规则。**连守着它的测试都是绿的**：
   那条测试断言「72o 查不到解」，而它确实查不到——因为**所有牌**都查不到。
   *教训*：断言「查不到」的测试，必须配一条断言「查得到」的。
2. **`shared_policy()` 的加载竞态**。先立「试过了」的旗再赋值共享对象，多线程各开一条
   会话打（`--workers 3`）时，后到的线程拿到 `None`，那个 bot 整场退回兜底——
   实测覆盖率 97% 掉到 49%，**不报任何错**。加锁修掉，并补了一条八线程抢跑的测试。

**深度守卫**：范围表是按某个深度解的，20bb 的桌子照 100bb 的表打是错的（那个深度该走
推/弃）。现在深度差出一倍以外就不查表。差一倍以内照用——翻前范围对深度没那么敏感，
「有解可用」比「刚好那个深度」更重要。

**接上之后的实测（3000 手，39.6 分钟，零作废、零对账失败，翻前 99.2% 照解走）**：

```
bb/100   -79.02 ± 99.35（95%）   区间跨 0，仍然分不出胜负
按钮位   -15.90（1500 手）
大盲位   -142.14（1500 手）      ← 亏损几乎全在这里
摊牌率   24.4%（此前规则层 11%）
```

**这个结果值得单独记一笔：接上解之后点估计反而更差了**（规则层那轮是 −24.94 ± 64.24）。
两者的差 54 bb/100 **在统计上分不开**（差值的 95% 区间约 ±118），所以**不能说是表把我们
打坏了**；但方向与机理是自洽的，而且指向同一个结论——

**翻前解让大盲防守得更宽（跟注 51.8%），可我们的翻后兑现不了那份权益。**
兑现模型假设的是「有位置/没位置各自能兑现多少」，那是**按能打的翻后**估的；我们真正的
翻后是蒙特卡洛权益 + 底池赔率的规则。于是：解按「兑现得了」的前提把范围放宽 → 我们带着
更宽的范围、在没位置的一侧、用规则打更多的翻后底池 → 摊牌率从 11% 涨到 24.4%，
钱从大盲位漏出去。**翻前解的质量受限于翻后的执行力**，这条以前只是道理，现在有数了。

**别据此回调翻前范围**：正确的修法是把翻后补上（M3 接 TexasSolver），顺带用实解校准
兑现系数（B 档）。拿翻前收紧去补翻后的窟窿，等于用一个错误抵消另一个错误。

**求解器加了一项能力**：`branch_nodes` 可以点名算**任意决策点**的分支价值
（原来只算根节点）。单挑整树解要在**防守者那个节点**上取「继续比弃牌好多少」给风格层
排序用，就靠它；六人桌的链式求解默认不算，成本一分没涨。


## 2026-08-18 · FR-6 强度基线：接上 Slumbot 打真对局

**交付**：新包 `src/holdem_slumbot`（协议翻译 / HTTP 会话 / 对局循环三分开）+
`scripts/play_slumbot.py`。我们的 bot 直接坐上去打，报**带 95% 置信区间的 bb/100**。

**策略接口就是 `callable(HandState) -> Action`**，`Bot.act` 天然符合。做法是把 Slumbot 的
动作串**回放成一份 `HandState`**——bot 拿到的局面与本地自对弈时一模一样，一行策略代码
都不用改。换 bot、换风格、甚至换成人来点，都不碰这一层。

**下注额是「本街」总额，不是本手累计**。上一条目里写成「本手总额」是因为校准脚本只用到
翻前，两者相同、分辨不出来。这回打多街样本一测就清楚了：
`b200c/kb200c/kb400c/kb1600c` 一共输 2400 ＝ 200+200+400+1600；若是本手累计，这四个数
必然单调递增。**这个口径错了，整场对局的 bb/100 会系统性地偏**，而且不会报任何错。

**每一手都拿它的 `winnings` 对账**（`protocol.check_result`）。弃牌终局逐筹码核对；摊牌
终局我们看不见对手的牌、判不了胜负，就核对「净得失只可能是 ±自己的投入或 0」。
这是整条链路唯一的外部真值——协议翻译一旦出错，会当场露馅，而不是悄悄变成一个
「看着挺像」的胜率。

**第一次实测**（「照解」风格，3000 手，29.6 分钟，**零作废、零对账失败**）：

```
bb/100   -24.94 ± 64.24（95%）  → 区间跨 0，分不出胜负
按钮位   +5.74（1500 手）
大盲位   -55.61（1500 手）
摊牌率   11.0%
```

**结论只能说到这一步**：3000 手分不出胜负，这正是「必须报区间」的意义——不给区间的话
「−24.9 bb/100」看着像个结论，其实全在噪声里。要把 −25 这个量级测实，得 **2 万手左右**
（区间随 √手数 收窄），按 101 手/分钟约三个半小时。**输在大盲位**（按钮位打平、大盲位
−55.6）与预期相符：Slumbot 按钮位 89.5% 开牌，而我们那边是兜底规则在防守。

**慢在网络**：一手三次往返，单条会话 30 手/分钟，三条并行 101 手/分钟。几条会话的结果
按「和 + 平方和」合并，口径与一条会话打同样多手完全一致。每条各存各的断点文件，
半小时的活儿断了不至于全丢。

**必须写在数字旁边的三条**：① 这是单挑 200bb，不是我们首攻的六人 100bb；② Slumbot 不是
GTO，赢它不等于接近均衡；③ **范围表是六人桌的，单挑一格都覆盖不到**——实测「照解走
0.0% 的翻前决策」，所以现在量的是**兜底规则层**的强度。要让它量解的强度，得再生成一张
单挑 200bb 的表（`solve_preflop` 本来就能解完整单挑树），那是下一步。

## 2026-08-18 · FR-4 批量对局与加速

**交付**：`holdem/batch.py`（纯逻辑）+ `scripts/play_batch.py`（进程池 / 打印 / 落库）。
一条命令让六个 bot 打一万手，产出 bb/100 与 VPIP/PFR/开牌/3bet/WTSD/W$SD。

**三条口径**是这个模块的全部价值所在：

1. **每手重置筹码**——现金局的评估口径，衡量策略本身而不是一次破产的运气。
2. **按钮每手右移一位**——六手一圈，每个座位在每个位置上的手数完全相同，
   位置差异互相抵消，剩下的才是风格的差异。
3. **bb/100 必须带置信区间**。单挑一手能输赢几百个大盲；不给区间的 bb/100 是没有意义的
   数字。区间靠「和 + 平方和 + 手数」算，所以**分片跑完直接相加**即可合并——
   `--workers N` 的结果与顺序跑口径完全一致（段之间只差种子与起始按钮位）。

**bb/100 全项目只有一处定义**（`batch.bb_per_100` / `bb_per_100_interval`），FR-6 的
Slumbot 基线共用它。两处口径不同的胜率数字比没有数字更糟。

**统计口径用手工编排的牌局逐条钉住**：盲注不算 VPIP、大盲过牌不算、跛入算 VPIP 不算 PFR、
**开牌者随后的 4bet 不能也算成 3bet**。这类错不会报异常，只会给出「看着挺像」的数字，
所以每一条都有一个编排好的牌局守着。

**实测吞吐**：六个 bot 单核约 41 手/秒（本机双核，`--workers 2` 约 49 手/秒），
一万手三四分钟。真正的成本在翻后蒙特卡洛，`--samples` 能再快两三倍——但那是拿决策
质量换时间，**量强弱时别动它**。

## 2026-08-18 · 补上 ADR-0004 第三条简化：防守者身后的挤压

**病根确认了**。前一天的校准把归因从兑现模型改到了 ADR-0004 的第三条简化
（防守者不担心身后）。这回把它建模补上，结果印证了那个判断：
**冷跟塌陷，3bet 纹丝不动，大盲（身后没人）一点没变**。

| | 冷跟（旧 → 新） | 3bet | 开牌（旧 → 新） |
|---|---|---|---|
| HJ 面对 UTG 开牌 | 19% → **6%** | 8% → 6% | UTG 20.8% → 14.8% |
| CO 面对 UTG 开牌 | 19% → **7%** | 8% → 6% | HJ 23.7% → 18.9% |
| BTN 面对 CO 开牌 | 24% → **13%** | 12% → 11% | CO 29.6% → 25.5% |
| SB 面对 BTN 开牌 | 28% → **20%** | 12% → 12% | BTN 41.3% → 38.5% |
| **BB 面对 SB 开牌** | 69% → **69%** | 15% → 15% | SB 38.8% → 38.8% |

真解里靠前位置几乎不冷跟、是「3bet 或弃牌」，正是因为身后有人会挤压。我们原来的表让
HJ 冷跟 19%——高出公开解一个数量级；现在 6%，量级对上了。

**怎么建的**：不进树（树里只有两个人，第三方进不来），而是给「防守者跟注、行动结束」
那个终局挂一个 `SqueezeRisk`：以概率 S 换成「被挤压」的收益，其余照常走翻后模型。
被挤压之后**再切一段子博弈真解一遍**（能弃能跟能 4bet），所以强牌打得回去、弱牌该弃就弃，
不是拍一个惩罚系数。挤压频率取身后各家**面对同一个开牌的 3bet 频率 × 0.6**，
按「谁先挤压」链式合成；用的是**上一轮**的频率，所以第一轮扫描等于不建模挤压。

**账要平**：被挤压时开牌者按弃牌处理，他投的 2.5bb 全部变成死钱由两人去争——桌上每一分
钱要么在两人的 `posted` 里，要么在 `dead_money` 里。**代价是这条支路不再是两人零和**：
底池有一部分被第三方拿走，`player_ev` 之和会小于死钱，差额正是挤压者的所得。
测试守的因此是不等式，不是等式。

**方向对，幅度过头**：开牌范围现在比公开解**紧 2–4 个百分点**（此前是松 2–3 个）。
最大嫌疑是「被挤压时开牌者一律弃牌」——那是他的**下界**（跟或 4bet 只会更好）。
要修得建三人子博弈，正是 ADR-0004 一开始就排除掉的多人积分。
**不按公开图表回调那个 0.6**：那等于拿别人的表当真值，与「正确性靠可利用度自证」的
口径相悖（HoldemResources 串行错值的坑还热着）。真校准走 ADR-0003 的 B 档。

**产物**：`preflop_ranges_6max_100bb.json` 重算（8 轮 / 23 分钟 / 173 KB），
最后一轮开牌频率变动 0.0023（比之前的 0.0053 更稳）。表里逐格存下了当时用的挤压概率
（UTG 开牌时 HJ 被挤 12%、CO 9%、BTN 5%、SB 3%、BB 0%）。为了验确定性，改完字段又
整跑了一遍：五个位置的开牌频率逐位一致。

**接到 bot 上量了一遍**（3000 手自对弈，同一个种子，FR-4 那套跑的）：

| 风格 | VPIP 旧 → 新 | PFR 旧 → 新 | 照解覆盖率 旧 → 新 |
|---|---|---|---|
| 照解 | 31.6% → **27.1%** | 17.0% → 16.8% | 57.7% → **65.8%** |
| 紧凶 | 20.4% → 16.9% | 13.2% → 11.9% | 63.0% → 73.6% |
| 松凶 | 36.4% → 30.8% | 27.0% → 22.9% | 60.3% → 72.7% |
| 岩石 | 12.0% → 10.1% | 7.6% → 7.0% | 74.7% → 83.6% |
| 跟注站 | 47.1% → 39.3% | 5.4% → 5.0% | 58.4% → 68.0% |

范围表覆盖不到的局面。

## 2026-08-18 · Slumbot 第一档校准：量级过关，但不改参数

**做了什么**：`scripts/calibrate_slumbot.py` 打了 2000 手（零错误、77 分钟），采集它在三个
局面的聚合频率，再把我们的模型在 12 组参数上各解一遍做对照。数据留在
`slumbot_frequencies.json` 里，换参数重跑时得跟同一份实测比。

**结论：量级过关，但不据此改默认参数**，理由与更正的归因写在 ADR-0003 里。要点是——
错配 6–8pp 且**方向相反**（前两个格子我们偏紧、面对 3bet 偏松），一个标量修不好；
而最佳拟合只把偏差从 7.2pp 降到 6.4pp，落在「单挑 200bb vs 六人 100bb」的噪声里。

**顺带更正了一个归因**。此前把「六人桌大盲防守偏宽」算在兑现模型头上；实测显示单挑下
我们的大盲反而比 Slumbot **弃得更多**（25% vs 16%）。所以病根更可能在 ADR-0004 的
第三条简化——子博弈里防守者不担心身后的挤压。**归因错了，后面要改的东西就全错了**，
这条比参数本身值钱。

**协议是打真请求摸出来的**，三处与直觉不同：`client_pos=1` 才是我们先说话；下注额是
**目标总额**不是增量；过牌要发 `k`，发 `c` 会被判 `Illegal call`。
（2026-08-18 补正：那个总额是**本街**的，不是本手累计——本脚本只用到翻前，两者相同，
所以当时分辨不出来。接对局时用多街样本量出来了，见当天的 FR-6 条目。）采集脚本自身也踩了两个坑：
**把我们自己的开牌当成它的应对**（读出「它面对开牌 100% 3bet」），以及**出错重打的半手被
重复计数**（20 手采出 28 个样本）——改成「整手打完才算数」。

**它的一个事实值得记住**：Slumbot 从不跛入，且开牌**只有 2.0bb 一个尺度**（895 次全是）。
所以对照时我们的模型也要关掉跛入，否则「开牌频率」比的是两件不同的事。

## 2026-08-18 · M1 第四段：风格层 + 换掉占位 bot

**交付**：`preflop_policy.py`（认局面 / 查表 / 翻译动作 / 风格层）、重写的 `bots.py`
（三层：翻前查表 → 翻前兜底 → 翻后启发式），范围表新增逐牌类 EV。FR-5 由此交付。

**「表里没有」必须能说出口**。查表层对跛入局、多人底池、4bet 之后、人数不符的桌一律回
`None`，交给规则兜底。表是按「一个开牌者 + 一个防守者」解出来的（ADR-0004），拿它去
指导多人底池就是拿不适用的解冒充精确解——PRD 里「诚实」那条非功能需求管的正是这个。
实测「照解」风格约 78% 的翻前决策走的是解。

**风格层踩到的三件事**，每一件都改变了实现：

1. **松紧不能用乘概率**。解里 100% 弃掉的牌，概率乘多少还是 0——「松」这个风格就永远
   打不出解以外的牌。改成**沿排序移动入池频率**：把 169 个牌类按「多值得入池」排好，
   再把频率整体拉到目标值。
2. **排序依据不能靠猜**。先用「对随机手牌的权益」当排序键，结果 65s 放宽到 2.5 倍都进不来，
   而 Q7o 早就进来了——松手风格打 K9o 不打同花连张，与真人完全不像。
   **求解器本来就算出了每手牌的开牌 EV**，把它存进表里当排序键，这个问题自然消失。
   （教训与 M1 第二段那次「别信抓来的公开图表」同源：手上有能自证的数就别用外部估计。）
3. **风格旋钮必须在兜底里也生效**。松风格会打出更多跛入/多人底池，而那些局面表不覆盖
   ——实测松风格有一半以上决策落在兜底上。兜底最初没吃 `aggression`，于是跟注站的 PFR
   高达 19%（该 2% 左右）。修完顺带发现**首位入池只有「开牌」一条路**（解里没有跛入），
   所以怂风格的跛入由**风格层**补上——这是风格层的行为，不是解的一部分，已写明。

**六人桌自对弈实测**（每档 300 手 × 6 座）：

| 紧凶 | 22.6% | 15.9% | 20–24 / 17–20 | 87% |
| 照解 | 31.6% | 19.4% | 解本身 | 78% |
| 松凶 | 37.6% | 28.8% | 32–38 / 25–30 | 60% |

## 2026-08-17 · M1 第三段（下）：六人桌按位置分解

**交付**：`preflop_chain.py`（分解 + 链式合成）、`preflop_ranges.py`（查表）、
`scripts/build_preflop_ranges.py`（离线生成），求解器新增**先验范围**与**分支价值**，
树支持**从中途切一段**。取舍见 ADR-0004。

**为什么不解整棵树**。六人 100bb 树有 623,070 个节点（单挑 40 个），每个决策节点带 169 个
信息集——纯 Python 一次遍历就要几分钟。两条出路里选了**按位置分解**而不是裁剪整树：
裁剪要砍掉 4bet 层，而 4bet 恰恰决定强牌怎么打；分解之后每个子博弈只有十来个节点，
动作集反而保留得更细。

**先验范围是关键的一小步**。子博弈里开牌者的范围**不能重解**——他只开一次牌，却要面对
身后五家，每家单独解会得到五个互相打架的开牌范围。所以求解器要能接受「你带着这个范围
走进来」，开牌决策留给外层。

**合成必须在归一化之前合并**。「防守者没弃牌时我这手牌值多少」是若干分支的合并，而每个
分支的除数（对手在该分支里还剩多少组合）**按牌类不同**——先除再加权就错了。为此
`BranchValue` 把分子分母分开存，`combine` 负责合并。

**一个自己写错的测试，反而钉住了公式**。第一版断言「合成 EV 落在各子博弈总 EV 之间」，
跑出来 6.15 > 4.60 判失败。查下去是**断言错了不是代码错**：合成用的是「条件在对方继续」的
EV，而子博弈总 EV 里混着「对方弃牌白得 1.5bb」那一支，被拉低了。改成正确的凸包判据
（全弃白得 + 各家条件继续 EV）之后，它反而变成一条真有力的测试——权重没归一、
或者取错了玩家一侧（子博弈里开牌者是玩家 1），都会立刻掉出凸包。

**外层那个 50/50 种子会漏进产物**。第一轮没有 EV 可依据，先验只能给均分；但它一旦进了
CFR+ 的平均，就会给**每一手垃圾牌垫上约 1.4% 的开牌频率**，而且永不消失。发现时构建
已经跑到第三轮，还是停下来改成「第一次更新时丢掉种子」重跑——这种误差不大但会写进
随包分发的数据里，越晚改代价越大。

**解出来的六人桌**（8 轮扫描、17.4 分钟、最后一轮开牌频率变动 0.005，产物 123 KB）：

| 位置 | 开牌 | 公开 GTO 量级 | 身后各家的弃牌率 |
|---|---|---|---|
| UTG | 20.8% | 17–19% | HJ 73 / CO 73 / BTN 73 / SB 78 / BB 52 |
| HJ | 23.7% | 21–23% | CO 70 / BTN 70 / SB 75 / BB 49 |
| CO | 29.6% | 27–29% | BTN 65 / SB 70 / BB 42 |
| BTN | 41.3% | 42–45% | SB 61 / BB 32 |
| SB | 38.8% | 40–45% | BB 16 |

**严格单调，量级吻合，早位略松**——偏松的方向正是 ADR-0004 里记的三条简化所预言的
（只有第一个不弃牌的人继续、防守者不担心身后）。**不把这几个数字当成基准**，
它们是「没跑偏」的旁证，真基准要等兑现系数校准。

**SB 每一轮都是 38.8%，纹丝不动**——查过不是没更新：SB 身后只有 BB，这个子博弈与桌型
无关（三人桌解出来是同一个数），第一轮就到了自洽不动点，之后每轮输入输出都相同。

**能看出模型糙在哪的一处**：总量频率落得很准（BB 面对 BTN 开牌弃 32 / 跟 56 / 3bet 12，
公开值约 40/45/15），但**逐手构成更糙**——66 以上的口袋对几乎全部 3bet，而真解里中对是
跟注为主。翻后模型没有牌面结构，中对的「好打」被高估了。界面上的翻前建议标 C 级
（启发式）就是为这种情况留的。

**验证**：

- 单测 **264 项全绿**（48 秒），慢测 16 项单独跑；系统 Python 下 251 项通过、2 项跳过。
- 新增测试覆盖位置口径、死钱账、子博弈切法、合成凸包、方向单调。
- **产物本身也有回归测试**（`test_preflop_ranges.py` 13 项）：开牌范围随位置单调变宽、
  强牌到处开、枪口位不开垃圾、大盲比小盲防守宽、每格都有 3bet 且不离谱、
  子博弈可利用度达标、写表时范围已稳定。范围表是数据，跑偏了算法测试看不见。
- **慢测抓到一条我写错的断言**：原以为「小盲身后人最少所以开得最宽」，实测三人桌小盲
  38.8% 反而窄于按钮 42.4%。断言错在把两件事混在一起——小盲还多背着「翻后没位置 +
  已投 0.5」。改成在**四人桌**比 CO 与 BTN（都不是盲注位，差别只有身后人数）。
  这条同时暴露了模型里 BB 防守偏宽，记进校准清单。

## 2026-08-17 · M1 第三段（上）：翻前树求解器

**交付**：`preflop_tree.py`（翻前抽象博弈树）、`realization.py`（翻后收益压缩模型）、
`preflop_solver.py`（树上的 CFR+），55 个新单测。路线与取舍见 ADR-0003。

100bb 的翻前范围没法像推/弃那样精确求解——「跟注看翻牌」值多少钱取决于翻后。把问题
切成两半：**下注序列完整展开成树**，**翻后压缩成一个数**（权益兑现系数）。

**先立正确性，再谈结果**。树退化成「全下或弃牌」之后，解必须与 `pushfold` 那套独立实现
对上，这一条同时验证了树、终局收益、共牌处理与 CFR+ 四处：

| | 树求解器（退化） | pushfold |
|---|---|---|
| 全下范围 | 58.45% | 58.34% |
| 跟注范围 | 37.26% | 37.32% |
| 小盲 EV | −0.045613 bb/手 | −0.045568 bb/手 |

逐手频率**故意不比绝对值**：均衡里无差异的牌可以任意混合，两套实现落在不同角上很正常
（实测最大差 0.15，全在近乎无差异的牌上）。比的是方向——对方几乎必推的牌，我们也得站在
推的一侧。

**一个真缺陷，被结果的形状抓出来**。第一版终局按权益分池，解完一看：大盲面对 2.5bb 开牌
只弃 11.3%，小盲面对 3bet 只弃 26.7%。病根是模型认定「有 30% 权益就能拿 30% 底池」——
真实牌局里弱牌的权益集中在少数牌面上，多街下注中多半要弃掉，公开求解器里体现为强牌兑现
超过 100%、弱牌不足 70%。加一个锐化指数 γ 把胜负比拉开（γ=1 时精确退化回按权益分池，
且份额仍恒好加成 1，守恒不破）：

| | 按权益分池 | 加 γ 之后 |
|---|---|---|
| 大盲面对开牌弃牌率 | 11.3% | 30.7% |
| 小盲面对 3bet 弃牌率 | 26.7% | 43.0% |

**另一个坑是报告口径，不是模型**。加完 γ 还看到「72o 有四成跟 3bet」，一度以为模型还有病。
其实 72o 在根节点 100% 弃牌，根本走不到那个节点——**CFR 只约束走得到的信息集，走不到的
地方策略是任意的**。深处节点的频率必须按**到达概率**加权，否则统计里混着一堆从未到场的牌。
现在 `action_range`/`action_frequency` 一律乘到达概率，`strategy_at` 保留原始策略并在
docstring 里写明它不该用来做统计。

**验证**：

- 单测 235 项全绿（37 秒），慢测 10 项单独跑（其中翻前求解 2 项约 78 秒）。
- 完整 100bb 单挑树（含跛入、开到 4bet）：1500 次迭代、约 75 秒，可利用度 **0.0026 bb/手**，
  小盲 EV +0.056 bb/手（单挑按钮有位置优势，方向与量级都对）。收敛大致 O(1/t)。
- 一条锁住因果链的测试：**锐化系数调大，大盲防守必须收紧**。没有它，整个模型层可能是死代码
  ——参数怎么改解都不动，也不会有测试红。

**性能的实测底数**：纯 Python 下每次遍历约 9000 次长度 169 的点积（把「共牌权重 × 收益」
预乘成每个牌类一行之后），单挑树约 47 ms/迭代。而**完整六人树有 62 万个节点**（单挑 40 个）
——下一段绕不开裁剪或按位置分解子博弈。

## 2026-08-17 · M1 第二段：翻前权益表与推弃纳什求解

**交付**：`equity_table.py`（预计算的 169×169 权益表 + 共牌权重）、
`scripts/build_preflop_equity.py`（生成工具）、`pushfold.py`（推弃纳什求解），
28 个新单测。

**权益表怎么算出来的**。精确枚举整表要 64 小时，所以走蒙特卡洛：每个对局 10,000 个样本，
每个样本随机抽一对**不冲突**的具体组合再抽公共牌——这样同时处理了花色配置的平均
（AKs 与 QQ 是否共花色）和共牌导致的不可能对局（AA 与 AKs 不能共用同一张 A）。
固定代表组合会在这两处系统性偏差。2 核跑 22 分钟，产出 112 KB，随包分发。
抽样验证：AA vs KK 估到 82.16%，公开值 81.9%。

**共牌权重是精确可算的**，与蒙特卡洛无关：拿着 AA 时对手能有的 AKs 组合恰好从 4 降到 2。
翻前求解忽略这一项会让门槛系统性偏移。

**换掉了虚拟对局**。第一版用 fictitious play，400 次迭代后可利用度仍有 0.005 bb/手
（≈0.5 bb/100）——对一个号称「纳什」的模块来说太大，而且是 O(1/√t)，靠加迭代救不动
（要好 10 倍得多跑 100 倍）。改成 **CFR+**（遗憾截零 + 线性加权平均），同时把内层循环
改成预计算行向量的点积：

| | 虚拟对局 | CFR+ |
|---|---|---|
| 可利用度 | 0.005 bb/手 | **< 1e-4 bb/手** |
| 迭代次数 | 400（撞上限） | 50–275（提前收敛） |
| 单次求解耗时 | 4.4 s | **< 1 s** |

**验证分三层，主验证不依赖任何外部数据**：

1. **可利用度自证**：解完直接算双方最佳应对还能多赚多少，全部低于 1e-4 大盲/手。
2. **逐手门槛对照公开纳什表**（比总百分比严格）：72o 2.7 vs 2.6、87s 6.6 vs 6.5、
   K2s 10.8 vs 10.7、22 15.1 vs 15.0——四个独立手牌全部吻合到 0.1bb。
3. **总量对照**：10bb 时全下 58.3%、跟注 37.3%，公开值约 54% / 36%。

**一处刻意不采信的公开数据**。同一来源的 A2o(8.1)、Q9s(8.9)、J8s(7.6) 三个跟注门槛与
我的解差 3–8bb。直接算 EV 判定：10bb 时 A2o 对上小盲 58.3% 的全下范围有 **49.8% 权益**，
而跟注只需 45%——跟注 EV −0.042、弃牌 −1.000，弃牌是接近 1bb 的错误。且 J8s 与 K2s 的
权益几乎相同（45.8% / 46.1%），公开值却给出 7.6 与 10.7 的 3bb 差距，不合理。判定为抓取
网页表格时读串行，不作为基准。**「选择性吻合」是源数据出错的典型信号**——真错了会全错。

**验证**：单测 180 项全绿（32 秒），慢测 8 项单独跑。

**下一段**：六人桌翻前范围表 + 风格层。

## 2026-08-17 · M1 第一段：范围基础设施与权益基准

**交付**：`ranges.py`（169 个起手牌类 + 范围记法）、`equity.exact_equity`（精确枚举），
30 个新单测。这是后面所有翻前工作的地基——范围表、风格层、HUD、复盘的 13×13 网格
全都以牌类编号为单位。

**编号即图表坐标**。牌类编号定义为 `行*13 + 列`，第 0 行是 A，右上三角同花、左下三角
不同花——正好是标准 13×13 图表的布局。前端拿到编号可以直接摆格子，不用再转换一次。

**先摸算力底数再选路线**。求值器实测 220,047 次/秒；单个翻前对局精确枚举要遍历
C(48,5)=1,712,304 个牌面（约 16 秒），整个 169×169 矩阵有 14,365 个对局
→ **约 64 小时，直接排除**。所以精确枚举只作基准值与验证用，整表预计算另想办法
（下一段处理）。

**权益基准对上了公开数值**（`pytest -m slow`，全枚举）：

| 对局 | 精确枚举 | 公开值 |
|---|---|---|
| AA vs KK | 82.64% | 81.9% |
| AKs vs QQ | 46.21% | 46% |
| AKo vs 22 | 46.96% | 47% |

AA vs KK 略高于公开值是对的：公开值是全部花色组合的平均，而 `AsAd vs KsKd` 花色重叠
最多、压制了 KK 的同花出路。方向与幅度都合理。

**顺带校验了蒙特卡洛估计器**。用「穷举全部对手底牌 + 全部河牌」算出精确的对随机手牌
权益，再和 `monte_carlo_equity` 比对——这是 `bots.py` 决策数值可信的前提，此前只是
假定它对。

**验证**：单测 155 项全绿（23 秒），慢测 1 项单独跑（46 秒）。

**下一段**：翻前权益矩阵的预计算方案 + 推弃纳什求解。

## 2026-08-17 · M0 第三段：服务端与网页牌桌

**交付**：`equity.py`（蒙特卡洛权益）、`bots.py`（占位规则 bot + 五种风格）、
`holdem_server/`（牌桌编排 + FastAPI + 单文件前端），共 42 个新单测。

**分层**：`table.py` 不 import 任何 Web 框架，因此牌桌逻辑能脱离 HTTP 单测；
`app.py` 只做请求翻译与状态推送。依赖也分层——`holdem` 包保持**零依赖**，
fastapi/uvicorn 只是服务端的可选依赖，pokerkit 仅供测试。

**bot 的一个真实缺陷，被统计测试逼出来**。第一版翻前用「对上全桌的多路权益」去比即时
底池赔率，结果枪口位 100% 弃牌——因为多路权益均值只有 1/6，而底池赔率要求 40%。
这个模型忽略了对手会弃牌、也忽略了隐含赔率。改成**翻前用单挑权益当牌力尺度、
翻后才用多路权益配底池赔率**。改完实测六人桌自对弈：

| 风格 | VPIP | PFR |
|---|---|---|
| 岩石 | 8.6% | 3.3% |
| 紧凶 | 21.3% | 10.5% |
| 松凶 | 40.8% | 28.5% |
| 跟注站 | 52.8% | 3.6% |
| 疯子 | 66.8% | 53.6% |

风格档位分得开，跟注站「松而不凶」的特征也对。**已知偏差**：紧凶的 PFR 偏低
（真人紧凶约 22/18，这里是 21/10.5），跟注偏多。占位实现不再调，M1 换成真策略。

**安全性质的一条**：`view()` 只公开英雄本人与摊牌者的底牌，其余一律为 null。
这条在 `test_table.py` 和 `test_server.py` 里各有一个专门的测试守着——泄露对手底牌
不是显示 bug，是让整个训练失去意义。

**验证**：

- 单测 **125 项全绿**（23 秒）。
- **端到端真跑**：起 uvicorn，用脚本走完整 HTTP 打了三手六人桌牌局——弃牌、跟注、
  摊牌、未跟注退款、分池、日志全部正确；三手牌都落进了 SQLite，PHH 能重放。
- 前端未在手机真机上验证，见下方待验证清单。

**下一段**：M1 —— 六人桌翻前范围表 + 风格层；单挑接 Slumbot API。

**开工前复核，推翻了一条方案判断**：设计方案原本把 AlphaHoldem 的非官方复现列为单挑对手
首选。细读其仓库说明后发现——官方从未开源、复现版是 TensorFlow+Ray、按 50bb 深度训练、
作者自述未收敛、强度只有定性描述而无任何 mbb/h 数字。已降级为备选，改以 Slumbot API 为

未知处理。

## 2026-08-17 · M0 第二段：PHH 牌谱与 SQLite 落库

**交付**：`phh.py`（牌谱读写）、`history.py`（决策点上下文）、`positions.py`（位置命名）、
`store.py`（SQLite 落库），共 33 个新单测。

**先调研再动手**。PHH 规范只说了字段名和动作记法，玩家编号与座位的对应关系得实测。
用 PokerKit 探出两条：

- 三人及以上：`blinds_or_straddles` 按位置套用，p1 是小盲、p2 是大盲、pN 是按钮，
  由 p3 先行动。
- **单挑是特例**：写入 `[5, 10]` 时实际发成 p1 押 10、p2 押 5，由 p2 先行动。
  也就是说两人局的 p1 是**大盲**，p2 才是按钮/小盲。凭直觉写必错。

**一个真的引擎 bug**，是靠外部互认测试逼出来的。PokerKit 拒绝了我们写的牌谱，二分定位到
`p8 cbr 1000`：当时对手最多只能凑到 400，加注到 1000 在 PokerKit 里根本不是合法动作。
原实现允许这种加注，靠事后「未跟注退款」把多余筹码退回，筹码结果是对的，但动作记录
不合法。改成把 `max_raise_to` 封顶在对手能跟到的最大额——结果完全不变，动作空间更干净，
也和主流平台一致。这类问题只有跨工具比对才会暴露，自己跟自己对账永远是自洽的。

**一处刻意保留的差异**：平分底池不能整除时，我们按赌场惯例从庄家左手第一个赢家起逐枚
多分，PokerKit 用自己的 divmod 策略。差异最多几枚筹码。保留标准规则，跨工具比对时给
零头容差，并写进了 ARCHITECTURE 与 CLAUDE.md。

**数据分层**：`hands.phh` 存牌谱原文作唯一事实来源，结构化表只是为查询建的索引，
任何时候都能从 PHH 重建。指标算错时先信 PHH。

**验证**：

- 单测 83 项全绿（2.8 秒）。系统 Python 下跳过 PokerKit 互认测试并保持 82 项通过——
  主程序不依赖 pokerkit。
- **外部互认**：120 手随机牌局写成 PHH 交给 PokerKit 重放，最终筹码逐一对上
  （零头容差如上）。
- **牌谱往返**：400 手随机牌局写出再读回，筹码、底牌、公共牌、是否摊牌全部一致。
- 压测脚本加入牌谱往返抽验（每 50 手一次）。**100 万手回归重跑**：加注封顶改动后全部
  不变量依旧通过，其中 20,001 手做了牌谱往返验证；221 秒，4,520 手/秒
  （比改动前的 5,126 手/秒慢约 12%，代价来自往返抽验，非引擎变慢）。

## 2026-08-17 · M0 第一段：引擎核心

**交付**：`src/holdem` 纯逻辑引擎 + 50 个单测 + 压测脚本。

做了什么：

- `cards.py` / `evaluator.py`：牌编码与 5–7 张求值。求值结果打包成单个可比较整数
  （`category << 20 | 五个决胜点数`），可直接当数据库排序键。
- `pots.py`：未跟注退款、主池/边池切分、按牌力分配。做成纯函数以便单独证伪。
- `state.py`：手牌状态机。发牌、盲注前注、下注轮、街推进、结算。
- `deck.py`：全项目唯一的随机数来源，种子必须显式传入。
- `actions.py`：动作与合法动作集，前端与 bot 共用同一份描述。

**验证**：

- 单测 50 项全绿（1.5 秒）。求值器采用双实现交叉验证：另写一份「枚举 7 选 5 +
  Counter 分类」的慢速参考实现，与位运算快路径在 6000 组随机与偏置手牌上逐一比对。
- 随机自对弈压测 **1,000,000 手**（2–9 座随机、筹码 2–5000 随机、含前注）：
  筹码守恒、无负筹码、净盈亏归零、发牌无重复、全部收敛，无一例外。
  耗时 195.1 秒，吞吐 **5,126 手/秒**（单核 Python），平均 6.6 个动作/手，摊牌率 88.2%
  （随机策略跟注偏多所致，属预期）。

**踩到的坑**（两处都是测试写错，不是引擎错）：

1. 验证「完整加注重开加注权」时，桌上只剩一个全下对手 —— 此时「无人可跟不得加注」
   这条规则会先生效，测到的根本不是重开权。必须留至少一个未弃牌未全下的第三方。
2. 造测试牌局时把 `A-4-9-2-5` 当成安全牌面，结果对手用 `3` 凑出了 A-2-3-4-5 轮子顺。
   构造牌面时要顺手检查顺子与同花。
