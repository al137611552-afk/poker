# 德扑训练台 · Windows 验证任务（给 agent 执行）

你是在 Windows 本机执行验证的 agent。这份文档是你的**任务书**。

- 代码版本以你拿到的包为准（进目录后 `git log -1` 或看包名）。
- 开发机是 **Linux 2 核 4G**，全回归在那边已绿。**你要验的是那台机器验不了的东西**：
  Windows 平台差异、求解器（要大内存）、以及浏览器/手机里的表现。
- **这份文档跟着代码走**（在 `docs/WINDOWS-VERIFY.md`），所以不写死版本号与条数——
  以脚本实际输出为准。

> **可能不是第一轮。** 2026-08-25 那轮已经验过一遍并发现了一个真 bug（解树内存），
> 已修。下面「最近一轮的改动」记着每次验证之后动了什么——
> **每次改完这份文档也要跟着更新**，否则下一个 agent 会照着过期的重点去验。

## 最近一轮的改动（2026-08-26）

### ① 上一轮那个内存 bug 已修——**多局面真解可以重跑了**

上一轮 `leak_report.py` 在 `--max-solves 3` 就卡死。根因不是机器不够：
`report = solver.solve(...)` 赋值时右侧先求值，新树建好的那一刻旧树还被引用着，
**峰值是两棵**（一棵十几 GB）。现在每解完一个就显式释放，峰值降到一棵。

所以请**重跑 `--max-solves 8`**（在 I 组里）。每个局面的进度行现在会打出
**当前峰值内存**，万一还是涨，一眼看得出是第几个开始的。

### ② 顶栏改成了标签条，面板互斥

上一轮反馈的两条（移动端按钮挤成一团、牌局和训练能同时摊开）都改了。
**人工清单里前三条就是验这个**，请重点转达。

### ③ 自检脚本多了 A2 组（前端静态检查）

四条：视图表引用的元素都存在、标签与视图一一对应、JS 语法、移动端断点。
这类断链**不会报错，只会让某个标签点了没反应**，所以值得静态查。
需要本机有 `node`；没有就会 SKIP（不影响其它组）。

## 你的工作分三步

### 第 1 步 · 装

```powershell
cd D:\holdem-trainer          # 解压后的目录，路径按实际改
py -m venv .venv
.venv\Scripts\pip install -e ".[dev]"
```

**判据**：`pip` 退出码为 0。
**失败就停**：把 pip 的原样输出报回来，后面全是噪声。

> `[dev]` 会自动带上 fastapi/uvicorn（`dev` 里自引用了 `[server]`）。
> 如果报 uvicorn 缺失，说明装的是旧包，请确认解压的是本次的 zip。

### 第 2 步 · 跑自检脚本（**你的主要工作**）

```powershell
$env:PYTHONPATH="src"
.venv\Scripts\python scripts\verify_windows.py --json verify.json
```

这一步会跑八组检查（具体条数以输出为准），**每条都有明确判据**，你不需要自己判断对错。
耗时主要在全回归（约 2~3 分钟）。

**读结果的规则**：

| 标记 | 含义 | 你要做的 |
|---|---|---|
| `✅ PASS` | 通过 | 不用管 |
| `❌ FAIL` | **代码有问题** | 把这条连同 `detail` **原样**报回来 |
| `⏭ SKIP` | 环境不具备 | 报出来，并说明为什么跳过 |

**退出码**：有 FAIL 时为 1，否则为 0。

> ⚠ **SKIP 不是通过。** 如果 C 组（求解器）整组 SKIP，说明最要紧的一组根本没验。

### 第 3 步 · 跑重活组（**开发机跑不动的那些**）

```powershell
.venv\Scripts\python scripts\verify_windows.py --only I
```

这三项在开发机（2 核 4G）上要么跑不动、要么慢到没法迭代，攒到这台机器上跑：

| 检查 | 内容 | 耗时 |
|---|---|---|
| 压测 | 20 万手随机自对弈，筹码守恒 + 牌谱往返抽验 + 无死循环 | 约 10~30 分钟 |
| 批量对局 | 一万手六人桌，统计要落在合理区间（VPIP 15~23%、WTSD <55%、零和） | 约 3~5 分钟 |
| 漏洞报告真解 | `leak_report --max-solves 8`，**要求解器**，验报告含 A/B/C 与可信漏损两列 | 很久，先做完 C 组 |

> **上一轮这条卡死在内存上，现已修**（见「本轮重点 ①」）。
> 如果还是涨到爆，请把**每个局面进度行里的峰值内存**贴回来——
> 那能直接看出是第几个局面开始涨的，比「跑了一半死了」有用得多。

**注意**：默认那条命令（第 2 步）**不含 I 组**，必须显式 `--only I` 或加 `--heavy`。
脚本会在结尾提醒你这一点。

> WTSD 那条判据的意思：范围感知默认是开着的，正常在 40% 上下；
> **60%+ 说明它没生效**——那是个真问题，不是数据波动。

### 第 4 步 · 人眼检查（脚本验不了的）

脚本最后会列出若干条必须人看的（条数见输出）。**你做不了这些**（需要真人看浏览器和手机）。
其中**前三条标着 `[UI]` 的是本轮改动**，请特别标注出来。
你要做的是：**原样把那份清单转达给用户**，并说明脚本已经验过哪些、这些是额外的。

## C 组（求解器）：需要你先编译

这组是最要紧的——它验的是 **EV 口径在这台机器上成立**，比任何界面问题都重要。
但它需要一个自编的求解器，官方预编译包**没有** `dump_evs` 这条命令。

### 编译步骤

```powershell
# 1. 装工具（如果没有）
#    需要 CMake 与 MinGW-w64

# 2. 取 console 分支的源码——**不是 master**（master 是 Qt 的 GUI 工程）
cd D:\tools\src
curl -L -o ts-console.zip https://codeload.github.com/bupticybee/TexasSolver/zip/refs/heads/console
# 解压，进入源码目录

# 3. 打补丁
git apply D:\holdem-trainer\docs\solver-build\0001-dump-evs.patch
#    或： patch -p1 < D:\holdem-trainer\docs\solver-build\0001-dump-evs.patch

# 4. 编译
mkdir build; cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
cmake --build . --config Release --target console_solver

# 5. 摆成后端要的样子
#    console_solver.exe 与 resources\ 放同一目录
$env:TEXAS_SOLVER_HOME="D:\tools\TexasSolver-console-build"
```

细节见包内 `docs/solver-build/README.md`。

### 编好之后

```powershell
.venv\Scripts\python scripts\verify_windows.py --only C
```

**判据**：三条全 PASS。其中最要紧的是第三条（慢测），它包含两道门：

- `test_solver_evs_match_the_hand_computed_spot` —— EV 对上手算的三个局面五个数
- `test_solver_evs_agree_with_the_evs_we_compute_on_the_tree` —— 两条独立路径互证

**这两条一红，说明口径翻译在这台机器上不成立**，那比界面问题严重得多，
把原样输出报回来。

### 编不出来怎么办

不要硬试超过一小时。把**卡在哪一步 + 原样报错**报回来，其余组照常跑
（C 组会自动 SKIP，不影响别的）。

## 几条你需要知道的约定

1. **不要"修复"失败的检查**。你的任务是发现与报告，不是改代码——
   这些检查各自守着一条容易错的默认值，改代码让它变绿多半是把门拆了。
2. **不要跳过 C 组**除非真的编不出来。它是这次验证的核心。
   **I 组也要跑**——那三项在开发机上跑不动，这台不跑就没人跑了。
3. **报告要贴原样输出**，不要转述。很多问题（编码、路径、locale）
   一转述就丢掉了关键信息。
4. 如果脚本本身崩了（不是某条检查 FAIL，而是整个脚本抛异常），
   那也是要报的——把 traceback 原样贴回来。
