# 架构

## 分层

```
客户端（浏览器 / 手机）——单文件前端，无构建步骤
        │  HTTP + WebSocket
FastAPI 适配层（app.py）——只做请求翻译与状态推送，不做决策
        │
牌桌编排（table.py）——手牌生命周期、bot 驱动、视图裁剪；不 import Web 框架
        │
存储层（store.py）——SQLite，引擎包里唯一的 IO 模块
        │
计算层——权益估算（现）／策略网络与求解器（M1 起）
        │
引擎层（src/holdem 其余部分）——纯逻辑，无 IO、无随机数
```

当前进度：**除策略网络与求解器外全部就位**。对手是占位规则 bot，M1 替换。

依赖也是分层的：`holdem` 包**零依赖**；fastapi/uvicorn 只属于服务端；
pokerkit 仅供测试。引擎因此能被任何环境直接引用，也便于将来把热路径换成 Rust。

## 视图裁剪：不泄露对手底牌

`TableSession.view()` 只公开英雄本人与**已摊牌**玩家的底牌，其余一律为 null。
这不是显示层的细节——如果客户端能拿到对手的牌，整个训练就失去意义。
`test_table.py` 与 `test_server.py` 各有一个专门的测试守着这条。

## 引擎层的设计约束

1. **纯逻辑**。`src/holdem` 里不出现文件、网络、时间、全局随机数。随机性以「一副已洗好
   的牌」的形式由调用方注入（`deck.py` 是唯一制造随机数的地方，且必须显式给种子）。
   这样任何一手牌都能由 (种子, 手数) 精确复现——牌谱回放、bug 复现、
   「同一副牌换个打法看结果」这三个功能都依赖它。
2. **整数筹码**。全程不用浮点，避免分池与统计出现累积误差。
3. **可比较的牌力分数**。求值结果是单个整数，可直接比大小、可存数据库当排序键。
4. **边池独立成模块**。`pots.py` 是纯函数，不依赖状态机，因此能被单独证伪。

## 关键数据结构

| 结构 | 位置 | 说明 |
|---|---|---|
| `HandConfig` | `state.py` | 一手牌的初始条件：筹码、按钮位、盲注、前注 |
| `HandState` | `state.py` | 可变的手牌状态；`clone()` 取快照供搜索使用 |
| `LegalActions` | `actions.py` | 当前行动者的完整可行动作描述，bot 与前端共用 |
| `Event` | `state.py` | 牌局流水，后续 PHH 牌谱导出的原始素材 |
| `HandResult` | `state.py` | 分池结果、退款、摊牌分数、每座位净盈亏 |

## 下注规则的实现要点

无限注德州扑克里最容易写错的是「加注权重开」。实现方式：

- `last_full_raise_level`：最近一次**完整**加注后的下注层级。
- `acted_at_level[seat]`：该座位本街最后一次行动时的下注层级（未行动为 -1）。
- 判定：座位可以加注 ⟺ `acted_at_level[seat] < last_full_raise_level`。

这一条同时覆盖了三种情形：大盲的后位选择权、短额全下不重开加注权、
完整加注后所有人重获加注权。

另有一条独立规则先行生效：**加注额封顶在「对手最多能跟到的额度」**。超出部分没有任何
人能跟，只会原样退回，记进牌谱还会被外部工具判为非法动作。这与主流平台的做法一致，
也顺带覆盖了「所有对手都已弃牌或全下时不能加注」的情形。

街结束的判定不是「所有人都行动过」，而是「所有仍能行动的人都行动过**且**本街投入
等于当前下注额」——短额全下会把下注额抬高，逼已行动的人再做一次跟/弃决策。

## 牌谱与存储

**PHH（Poker Hand History）是唯一事实来源。** 它是 TOML 文本格式，由多伦多大学计算机
扑克研究组提出、PokerKit 原生支持；选它而不是自造格式，是为了牌谱能被外部工具读取，
也能读进外部牌谱。数据库里 `hands.phh` 存原文，结构化表（`hand_players` /
`hand_actions`）只是为查询建的索引，任何时候都能从 PHH 重建。

PHH 有两个反直觉之处，都由 `phh.py` 封装：

1. 玩家编号 p1..pN 不是座位号——p1 是小盲、pN 是按钮。
2. **单挑是特例**：参考实现在两人局把盲注数组反向套用，写 `[5, 10]` 时实际是 p1 押 10、
   p2 押 5，由 p2（按钮/小盲）先行动。因此单挑时 p1 是大盲。

`history.py` 负责把事件流还原成「决策当时的局面」（底池、面对的下注、还剩几人能行动、
位置），M2 的所有统计指标都从这一层的 `ActionRecord` 推导，不再各自解析事件流。

## 与外部工具的一处已知差异

平分底池的零头分配：本项目按赌场惯例，从庄家左手第一个赢家起逐枚多分；PokerKit 用
自己的 divmod 策略。结果差异最多几枚筹码，且只出现在多人平分且不能整除时。
跨工具比对牌谱要给零头容差。

## 对手策略的现状与去向

`bots.py` 分三层，各管一段：

| 层 | 覆盖 | 依据 | 置信度 |
|---|---|---|---|
| 翻前查表 | 首个开牌、面对开牌、面对 3bet | 解出来的范围表 | B（模型解，兑现系数未校准）|
| 翻前兜底 | 跛入、多人底池、4bet 之后 | 单挑权益 + 底池赔率 | C |
| 翻后 | 全部 | 多路权益 + 底池赔率 | C |

**表覆盖不到的局面明确回 `None`**，交给兜底——不拿一份不适用的解冒充精确解，这是 PRD
「诚实」那条非功能需求的落点。实测「照解」风格约八成翻前决策走的是解，松风格因为会打出
更多跛入/多人底池，走解的比例掉到四成上下。

风格层只有两个旋钮，都作用在解上：`looseness` 沿**求解器算出的逐手 EV** 排序移动入池
频率，`aggression` 调整加注与跟注的配比。两处反直觉的设计写在 CLAUDE.md 的已知坑里
（松紧不能用乘概率、首位的跛入要由风格层补）。

一个值得记住的教训：翻前不能用「对上全桌的多路权益」去比即时底池赔率。多路权益的均值
只有 1/人数，而底池赔率会要求 40%，结果是任何牌都弃。翻前改用**单挑权益**当牌力尺度，
翻后才用多路权益配底池赔率。

按设计方案，真正的策略分三层接入（接口保持不变，替换实现）：

- **L1 基准策略**：翻前求解范围表 + 翻后单挑求解器 + 策略网络兜底（M1、M3）
- **L2 多人桌代理**：范围跟踪 + 多路权益 + 规则（M4）
- **L3 风格层**：把风格向量作用在 L1/L2 的动作分布上（M1）

## 翻前求解这条链

L1 的翻前部分已经建好，四层各司其职（细节见 ADR-0003、ADR-0004）：

```
preflop_tree.py    公共博弈树：离散下注尺度、完整下注序列，不含任何牌
                   ├ PreflopConfig  整桌（单挑可直接解）
                   └ SubgameConfig  从中途切一段（任意死钱/位置/已加注几次）
realization.py     翻后压缩成一个数：权益兑现系数 + 归一化份额（终局严格零和）
preflop_solver.py  树上的 CFR+（两人）：先验范围进、逐牌类 EV 与分支价值出
preflop_chain.py   六人桌拆成一串两人子博弈，合成开牌 EV，外层 CFR+ 迭代
                   └ 挤压：防守者跟注的那个终局按概率被身后第三方接管（ADR-0004 修订）
preflop_ranges.py  读离线算好的范围表；运行时只查表，不求解
```

产物有两张，**来路不同、自证方式也不同**：

| 产物 | 怎么解的 | 自证 | 耗时 |
|---|---|---|---|
| 六人 100bb | 按位置拆成子博弈再链式合成（ADR-0004） | 范围还变不变（`max_change` 0.0023） | 约 23 分钟 |
| **单挑 200bb** | **整树直接精确解**（ADR-0003） | **可利用度 0.0008 大盲/手** | 约 23 秒 |

单挑那张是给 FR-6 用的：Slumbot 就是单挑 200bb，深度与人数都要对上。`preflop_policy`
**按人数分发**，深度差一倍以外就不查表（那种深度该走推/弃）。

三条与直觉相反、值得单独记住的性质：

1. **深处节点的频率必须按到达概率加权**。CFR 只约束走得到的信息集；直接读策略表会把
   从未走到那里的牌一起统计进去。
2. **合成子博弈价值要在归一化之前合并**。每个分支的除数（对手在该分支里还剩多少组合）
   按牌类不同，先除再加权就错了。
3. **带挤压的子博弈不再是两人零和**。底池有一部分被第三方拿走，两人的 EV 之和会**小于**
   死钱，差额正是挤压者的所得。这是模型的应有之义，测试守的是不等式。

正确性不依赖外部数据：可利用度自证 + 把树退化成推/弃后与 `pushfold` 交叉验证。
**但翻后模型的参数是未校准的假设**，所以翻前建议目前只能标 C 级（启发式）。

## 量强弱这条链

策略改动有没有变强，靠两个入口回答，**bb/100 与置信区间的算法只有一处定义**
（`metrics.py`），连牌谱库的玩家汇总也共用它：

```
batch.py                 一桌 bot 自对弈上万手（FR-4）。纯逻辑：给配置、回统计。
  ├ 每手重置筹码、按钮逐手右移 → 位置差异抵消，剩下的才是策略差异
  └ shard / merge        分片并行，按「和 + 平方和 + 手数」合并，口径与顺序跑一致
holdem_slumbot/          外部标尺（FR-6，ADR-0002）
  ├ protocol.py          动作串 ↔ HandState 的回放；每手拿 winnings 对账（纯逻辑）
  ├ client.py            HTTP 会话——全项目唯一联网的地方
  └ match.py             对局循环；策略接口就是 callable(HandState) -> Action
```

回放这一步是关键：bot 在 Slumbot 桌上拿到的 `HandState` 与本地自对弈时**完全一样**，
所以「换个策略去打外部标尺」不需要改任何策略代码。

## 翻后求解这条链（M3，ADR-0005）

```
holdem_solver/
  request.py   局面 → 求解器命令文件（纯逻辑）。范围必须逐类展开——`99+` 会让求解器 abort
  result.py    策略树 JSON → SolvedNode（纯逻辑）。求解器的 OOP 是 player 1，读进来就翻译
  backend.py   跑 TexasSolver CPU 版 + 按指纹缓存（唯一碰进程与磁盘的一层）
```

三条把形状定死的事实：**只解两人**（多人底池不打分）、**dump 里没有 EV**（EV 损失要我们
自己在解出来的树上算）、**一个局面几分钟**（只服务复盘，实战现解不可行；缓存是必需品）。
