# ADR-0006：自己编译求解器——取回「具体组合」与「直接问 EV」

- 日期：2026-08-19
- 状态：**进行中**（第 1 段已验证；第 2 段 `dump_evs` 已实现并对上手算；接进复盘打分待做）
- 相关：ADR-0005（翻后求解后端）。本 ADR 不推翻它，是在它上面加一层：
  **仍然只调用不分发的 AGPL CPU 版 TexasSolver，只是二进制从「官方预编译包」换成「我们自己编的」**

## 背景

FR-10 在 Windows 上真跑（2026-08-19，见 DEVLOG）撞墙，把两件事逼到了台面上：

1. **翻牌决策的 EV 需要整棵树导满三层**（dump 里没有 EV，只能自己在树上积期望），
   而那正是 pilot 判过死刑的方案 A——真实规模 10 GB 级产物。
   逐街分别解（方案 B）只解得了转牌与河牌，**翻牌决策在它手里根本算不出数**。
2. **求解器的范围输入只认 169 个牌类**，滚范围只能按牌类聚合，同花听牌被抹平——
   方案 B 的保真度上限。

两个问题的根都在「我们只能通过预编译二进制的 dump 跟求解器说话」。
用户拍板：**从源码编译，直接向求解器要 EV**。

## 第 1 段实测到的事实（2026-08-19，本机 2 核 / 3.6 GB）

| 事项 | 结论 |
|---|---|
| **源码怎么编** | 官方有专门的 **`console` 分支**（CMake，就是我们手上那个预编译 console 包的来源）。master 分支是 Qt 的 GUI 工程，`PokerSolver.h` 里带 `QDebug`/`QFile`——**别照着 master 编** |
| **要不要 Qt** | **不要**。`ldd console_solver` 只有 libstdc++/libgomp/libc；fmt、googletest、pybind11 三个依赖都随分支的 `ext/` 一起发，无需联网拉子模块 |
| **本机编得动吗** | 编得动。`cmake -DCMAKE_BUILD_TYPE=Release` + `make -j1`（**必须 -j1**，2 核 3.6 GB 并行会顶到内存），34 个编译单元，静态库 4.7 MB |
| **具体组合喂得进去吗** | **喂得进去**。console 分支的 `PrivateRangeConverter` 有 `range_len == 4` 分支（`has_exact_combo`）。实测 `set_range_ip AhKs,QdQc,7h6h` 正常求解，dump 里 `AhKh` 独立成条。**我们手上那个 v0.2.0 预编译包会 SIGABRT，是版本差异，不是格式限制** |
| **代价** | 范围里一出现具体组合，它**自动关掉花色同构**并打印警告（同构假设四门花色对称，具体组合破坏了这个前提）。同构是翻牌求解的主要加速手段之一，**关掉之后慢多少还没量** |
| **dump 里有 EV 了吗** | **还是没有**。EV 仍然得自己算，或者自己加 |
| **EV 拿得到吗** | **拿得到**。`PCfrSolver::actionUtility` 里的 `all_action_utility[action_id][hand_id]` 就是「某个动作、某手牌」的收益，逐组合的，本来就在算，只是没往外吐 |
| **能原地换掉旧二进制吗** | 能。同一份命令文件，新旧二进制 dump 出来的动作标签逐字相同；`tests/test_solver*.py` 与 `test_review.py` 的 3 项慢测在新二进制上全绿 |

## 决策

1. **求解器二进制改为自己编译 `console` 分支**，`TEXAS_SOLVER_HOME` 指向自编产物。
   预编译包留着当对照——**新旧二进制必须在同一份命令文件上给出相同的树**，这是每次
   重编之后的第一道验收。
2. **EV 走「给 console 加一条命令」，不走 ctypes FFI**（与最初设想的 FFI 形式不同，
   实质相同：都是从源码编译、直接向求解器要 EV）。理由：
   - `backend.py` 至今是**全项目唯一碰进程与磁盘的地方**，加一条命令不动这条边界；
     ctypes 会把一个 C++ 对象的生命周期搬进 Python 进程，ABI、异常、OpenMP 线程全成我们的事。
   - 按指纹缓存那套照用不误（查询进指纹即可）。
   - Windows 那台只要照样编一次，不用再管 `.dll` 的调用约定。
   - **要问的线路在求解之前就全知道**（`plan_review` 先出计划再求解），
     所以「一次进程跑完求解 + 全部查询」不吃亏。将来复盘界面需要反复追问同一个解，
     再上常驻进程或 FFI，那时 C++ 那一侧的 EV 遍历代码是同一份。
3. **AGPL 边界照旧、并且更严**：源码与我们的补丁**都不进这个仓库**，仓库里只放
   `docs/solver-build/`（构建步骤 + 补丁文件）。产物不随包分发，没装就明确报错。
4. **具体组合先不默认打开**。它关掉同构、代价未知；等量到「同构关掉之后慢多少」
   再决定滚范围要不要逐组合喂回去。**在那之前，方案 B 的保真度上限依然成立。**

## 已知代价与风险

- **多了一件要维护的东西**：两台机器各要编一次；重编之后要跑「新旧二进制同树」对照 + 慢测。
- **补丁跟着上游走**：我们改的是 AGPL 源码，上游一动补丁就可能对不上。
  所以补丁要**小而集中**——只加「一条命令 + 一次 EV 遍历」，不重构人家的东西。
- **同构关闭的代价没量**：具体组合这条路可能贵到不值得，那就退回按牌类聚合。
- **EV 的口径要对账**：`actionUtility` 给的是 CFR 口径的收益（按对手到达概率加权），
  跟我们 `evaluate.py` 的「最终底池 × 份额 − 从这个局面起的投入」不是同一个归一化。
  **接进来的第一件事是拿河牌那个手算局面对账**（跟注 −3.0000 / 弃牌 −0.0000 / 全下 −9.0000
  三个数是现成的硬基准），对不上就是口径没翻译对，别调系数糊过去。

## 第 2 段：`dump_evs` 已落地并对账通过（2026-08-21）

补丁在 `docs/solver-build/0001-dump-evs.patch`（7 个文件、230 行增），
在干净源码上 `patch -p1 --dry-run` 验过可用。

**命令**：`dump_evs <文件> <player> [a1|a2|...]`。
线路用 `|` 分隔而不是空格——动作标签本身含空格（`BET 30.000000`）。
顺带放宽了上游的命令解析：它按**每个**空格切、超过两段就 throw，
于是任何带空格的参数都表达不出来；现在改成「第一个空格之后全是参数」，
既有命令的解析结果一字不变。

**口径（这是最要紧的结论）**：

> 我们的 EV = 求解器 EV + **该节点上自己已投进底池的份额**

拿那个「结果完全确定」的河牌局面对账（OOP 全暗三条、IP 全一对，底池 6、
双方各投 3），三个局面五个数**零误差**：

| 谁 · 在哪 | 求解器 | 加回已投的 3 | 手算 |
|---|---|---|---|
| OOP 在根（必赢底池） | +3 | 6 | 赢下整个底池 |
| IP 在根（必输、未再投） | −3 | 0 | 一分不亏地弃掉 |
| IP 面对全下 · FOLD | −3 | 0 | 同上 |
| IP 面对全下 · CALL | −12 | −9 | 白扔九个大盲 |

已钉成慢测 `test_solver_evs_match_the_hand_computed_spot`。

**路上踩的两个坑，都属于「看着像但错了」**：

1. **归一化要用「到该节点的 reach」，不是原始组合权重**。遍历返回的是
   *按对手 reach 求和* 的收益，除以原始权重就会**过度除以那条线路的频率**。
   前两个数据点都在**根节点**（reach 尚未被策略加权），一个也发现不了；
   往下走一层才暴露——所有数恰好是真值的一半。
   **教训：对账点必须包含「走过至少一步」的节点。**
2. **`getReachProbs()` 与 `private_combos` 不是同一套索引**，混用是越界读，
   结果是**整齐的 0**而不是崩溃。改成照 `printExploitability` 的做法，
   在类内部从 `private_combos` 自建 reach。

**另加**：`TexasSolver.supports_evs()` —— 官方预编译包不认这条命令，
不查就会红成一片，而真原因埋在求解器日志的一行 `command not recognized` 里。
判据是在二进制里找命令名，比真跑一次便宜几个数量级。
