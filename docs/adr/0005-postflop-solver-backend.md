# ADR-0005：翻后求解后端——用 CPU 版 TexasSolver，不是 GPU 版

- 日期：2026-08-18
- 状态：已接受（实现：`src/holdem_solver` 适配层）
- 取代：设计方案 v0.1 与立项记录里「求解后端走 TexasSolver **GPU**，CPU 路径作降级」这条

## 背景

M1 收尾时对 Slumbot 打出了 3000 手基线：**−79.02 ± 99.35 bb/100**，亏损几乎全在大盲位
（−142 vs 按钮位 −16）。机理清楚——翻前照解出来的范围把大盲防守放宽到跟注 51.8%，
而我们的翻后是「蒙特卡洛权益 + 底池赔率」的规则，兑现不了那份权益。
**翻后没有解，是眼下唯一有量级意义的缺口**，所以 M3 提前启动。

立项时已经拍板用 TexasSolver。这次落地前做了三项实测，其中一项推翻了原来的后端选择。

## 实测到的事实（2026-08-18）

| 事项 | 结论 |
|---|---|
| **GPU 版** | **Windows-only、只有 GUI、闭源、EULA**，仓库明说「public repo 不代表 gpu_solver 源码开源」，**没有任何 headless / 命令行 / API 求解接口**（只带一个看结果的 viewer）。→ **无法自动调用** |
| **CPU 版** | AGPL-3.0，有 `console_solver` 命令行**与** C FFI（`api.so/dll`，官方给了 Python ctypes 例子），Linux/Windows/macOS 都有预编译包。**本机 Linux 直接跑通**，无缺失依赖 |
| **速度** | 本机双核：小树 20 次迭代 48 秒、可利用度降到 4%；官方基准 6 线程 SPR=10 翻牌局面 172 秒到 0.275%、吃 1.6 GB 内存 |

## 决策

1. **自动化后端 = CPU 版 TexasSolver**（console / FFI）。GPU 版降级为**人工工具**：
   它能在 Windows 上手点着看某个局面，但进不了任何自动流程。
2. **求解器不随包分发**。AGPL-3.0 意味着：自用没问题，**跟着我们的包一起发就要同协议开源**，
   拿它做联网服务同样不行。所以 `holdem_solver` 只**调用**，路径由 `TEXAS_SOLVER_HOME` 给；
   没装就明确报错并给安装说明，**绝不悄悄退回近似**（PRD「诚实」那条）。
3. **翻后解只服务复盘，不服务实战**。几分钟一个局面，实战中现解不可能。想让 bot 翻后变强
   得走「离线批量解 → 蒸馏成紧凑策略」，那是另一段工程，不在 M3 里。

## 由此定死的三条约束

1. **只解两人**。TexasSolver 是两人求解器，多人底池它不解——所以复盘打分只能覆盖
   「翻牌时只剩两个人」的手牌，多人底池一律标「不打分」，不许拿两人解去凑。
2. **dump 里没有 EV**。产物只有每个决策点的**策略**（逐具体组合）与发牌节点信息，
   `ev` 字段一个都没有（官方样例里也没有）。所以 FR-9 的「EV 损失」得**我们自己在解出来
   的树上算**——终局收益 + 到达概率，与 `preflop_solver` 同一套办法，只是终局换成真实摊牌。
   **拿「你打了低频动作」冒充 EV 损失是不诚实的**，不做。
3. **导整棵树很贵**。`set_dump_rounds 1` 只导一层（十几 KB），官方样例导两层就 27.7 MB。
   算 EV 需要更深的树，所以树的规模（下注尺度个数）要克制，且要按局面缓存。

## 格式上三个实测才知道的坑

1. **范围不能用 `+` 记法**：`set_range_ip 99+` 会抛 `format not recognize` 然后 **SIGABRT**
   （退出码 134，什么都不输出）。必须逐个牌类展开。我们自己的记法里 `+` 到处都是，
   这条最容易原样送进去。
2. **金额可以是小数**：`set_pot 12.5` 可用。于是全程用**大盲**当单位，不必迁就成整数筹码。
3. **它管 OOP 叫 player 1、IP 叫 player 0**（实测：IP 只放 AA、OOP 放小对子，根节点
   `player=1` 里出现的是小对子）。读进来时翻译成我们的口径（0=OOP），有测试守着——
   取错一侧的解看着仍然「像那么回事」，这是本项目栽过的同一类跟头。

## 补充实测（2026-08-18，接复盘时才暴露）

这三条在「只解一次、只读根节点策略」的用法下看不出来，接上 FR-9 的逐点打分才暴露：

4. **`set_bet_sizes` 同一格（谁,哪条街,什么动作）只能发一条命令**。发第二条是**覆盖**
   而不是追加，而且一声不吭——33/63.6/75 各发一条，树里只剩 75% 那一个尺度。
   多个尺度写在同一行：`set_bet_sizes ip,flop,bet,33,63.6,75`。
5. **它把算出来的下注额取整到整数单位**。底池 5.5 打 33% 应是 1.815，树里是
   `BET 2.000000`＝36.4%。金额本身可以是小数（第 2 条仍然成立），取整的是它算出来的
   下注额。于是**命令文件里的单位改成 1/10 大盲**（`SolveRequest.scale`，粒度 0.1bb），
   解回来的金额除回大盲；对外的字段一律还是大盲。实测确认：一条命令给三个尺度，
   树里三个下注选项齐了，实际百分比 32.7 / 63.6 / 74.5。
6. **要在解出来的树上算 EV，dump 必须导满到河牌**（翻牌局面＝`dump_rounds=3`）。
   只导一层连**翻牌上的**决策都算不了：EV 是把后面的期望积出来的，而任何一条走到转牌的
   路在一层的 dump 里都没有下文。

**代价实测**：翻牌局面、双方各 3 个牌类、有效筹码 20bb、三个下注尺度 + 全下、
`dump_rounds=3` → **产物 163.7 MB**、求解 156 秒（2 线程）、在树上给一个决策点打分 1.4 秒。
换成真实范围（几十个牌类）与 97.5bb 的深度，产物是 GB 量级——**「每手牌解一次翻牌树」
这条路走不通**。下一段要定的就是复盘的求解粒度（候选：逐街分别解、只解被问到的那个
决策点所在的街、或者走 C FFI 直接问 EV 而不 dump 整棵树）。

## 求解粒度定了：逐街分别解（2026-08-19，Windows pilot 实证）

上一节留的问题——「每手解一次整棵翻牌树走不通，那走哪条」——用一轮 pilot 量清楚了。
**实测环境**：Windows、CPU 版 8 线程、`max_iterations=20`、`accuracy=1.0`（量的是相对成本，
**不是跑到收敛**，见下面的「这批数字要打的折扣」）。

| 方案 | 树 | 求解时间 | 产物 | 结论 |
|---|---|---|---|---|
| A 整树一次解（原做法） | 1 棵大 | 325s（20bb） | **822.8 MB**（20bb） | ❌ 判死刑 |
| B 逐街分别解 | 3 棵小 | 69–103s/棵（20bb） | **~0.2 MB/棵** | ⭕ 选它 |
| C 只解被问到的那条街 | 1–3 棵 | 同 B 单棵 | 同 B 单棵 | ⭕ B 的特例，可作起步 |

标度实测（决定成本的是什么）：

- **范围大小不是主导**：3+3 牌类（~20 组合）69.2s vs ~30 牌类（~900 组合）102.9s——
  组合数翻 45 倍，只慢 1.5 倍。真实范围（OOP 1127 / IP 543 组合）落在这个量级里。
- **筹码深度线性主导**：20bb 102.9s → 50bb 257.8s → 97.5bb 434.4s（深度 ×5，时间 ×4.2）。
- **下注尺度影响小**：2 个尺度 → 3 个尺度，时间基本不变。
- **`dump_rounds` 才是产物爆炸的唯一原因**：同一局面 1 层 ~0.2 MB / 102.9s，
  3 层 **822.8 MB** / 325.1s。真实规模外推：**10 GB 级、单手数十分钟**。
- **缓存命中 0.0s**（读盘即得）：同一局面只有第一次贵。

**决策：走 B——每街一棵 dump 1 层的小树，转/河的范围从上一街的解滚出来。**
理由是 A 的产物必然 GB 级（这是 dump 层数的性质，不是参数没调好），而 B 的每棵树都在
MB 级、分钟级，且缓存命中后几乎免费。C 不是独立方案，是 B 只解一条街的特例，可以当起步。

### 这批数字要打的折扣（别当成可用解的价格）

pilot 跑的是 `max_iterations=20 / accuracy=1.0`，解出来的可利用度是 **17.1%（20bb）/
35.7%（50bb）/ 59.5%（97.5bb）占底池**——**三个都远没收敛**（可用的解要 0.5–1%）。
所以：

- 表里的「秒」是**跑 20 次迭代的价钱**，不是「解到能用」的价钱。
- 更要命的是**越深越不收敛**（同样 20 迭代，20bb 17% vs 97.5bb 59.5%），说明真实成本
  比「深度线性」还要陡——收敛所需迭代数本身随深度涨。
- 因此「B 三棵树十几分钟」是**乐观下界**。真实预算要另外量一次：
  97.5bb 单棵 dump1、`accuracy=0.5` 跑到收敛实际要多久。**这条没量之前，别拿十几分钟去
  承诺任何界面上的复盘时延。**

### B 的保真度上限：街与街之间只能传 169 个牌类（2026-08-19 实测）

滚范围要把上一街解出来的权重喂回下一街，而**求解器的范围输入只认 169 个牌类**：

```
set_range_oop AhKs,AA   →  terminate: range str AhKs len not valid（SIGABRT，无输出）
set_range_oop AA,KK:0.25 →  正常求解（牌类 + 权重可用，我们已经在用）
```

这是继「`+` 记法」之后**第二个会让求解器直接 abort 的范围格式坑**，长度校验只放行 2–3 字符。
后果：解出来的策略是**逐组合**的（`AhKh` 与 `AsKc` 在两张红桃的翻牌上完全是两回事），
但滚回下一街时只能按牌类聚合权重——**同花听牌在街与街之间会被抹平**。
`AKs` 的四个组合里只有一个是同花听牌，聚合后四个都拿到平均权重。

预编译包里**没有 .so / .h**，`resources/python` 那份 `bindSolver` 样例引用的模块也没随包发——
**C FFI 要自己从源码编译**（AGPL C++ 工程），不是解压就能用。所以「走 FFI 直接喂逐组合权重」
现在是一笔要单独立项的成本，不能顺手做。

## 验证

- 命令渲染与策略解析是纯逻辑，用**真求解器跑出来的样本**（`tests/data/texassolver_flop.json`）
  当基准；手写样本挡不住格式漂移。
- 真跑一次的测试标 `slow`，没装求解器自动跳过。
- 求解器自己报的**可利用度**（占底池百分比）随缓存一起存下来：没解到要求精度的解，
  `SolveReport.meets()` 会说不。

## 影响

- 新增 `src/holdem_solver`（`request` / `result` / `backend`），与 `holdem_slumbot` 同样的
  三层切法：纯逻辑 / 唯一碰 IO 的那层 / 对外接口。
- 设计方案里「GPU 优先、CPU 降级」的表述作废，PRD 的计算路线一栏要跟着改。
- 8GB 显存的预算约束**在这条路线上不再是约束**——CPU 版吃的是内存与线程，不是显存。
