# ADR-0002：单挑强对手的来源

- 日期：2026-08-17
- 状态：已接受（取代设计方案 v0.1 中"以 AlphaHoldem 复现权重为首选"的判断）

## 背景

设计方案最初把 `bupticybee/AlphaNLHoldem`（AlphaHoldem 的非官方复现）列为单挑对手的首选，
理由是它公开了 checkpoint、模型小、推理快。开工前复核该仓库的说明，发现四条此前未掌握的
事实，足以推翻这个排序。

## 复核到的事实

| 事项 | 内容 |
|---|---|
| 官方实现 | AlphaHoldem（AAAI 2022）**从未开源**代码或权重，论文中的 111.56 mbb/h 属于官方模型，不能挪用到复现版头上 |
| 框架 | 复现版是 **TensorFlow + Ray**，不是 PyTorch；原计划的"转 ONNX"要多一层 tf2onnx，且旧版依赖在新 Python 上能否装起来未知 |
| 筹码深度 | 训练使用 **50bb**，而非标准的 100bb / 200bb。深度不同策略结构就不同 |
| 收敛性 | 作者自述十亿手自对弈、上千个 checkpoint 之后"模型似乎仍未收敛" |
| 强度证据 | 仅"几位职业玩家觉得它的动作合理"，**无任何 mbb/h 数字**，连自测都没有 |

## 补充：本地大蓝图整条路线排除（用户实测反馈）

DecisionHoldem 的蓝图**吃 100 GB 以上内存仍不够**，在目标机器（RTX 4060 Ti 8 GB 的
普通台式机）上没有任何可行性。这与 HUNL 蓝图的已知规模吻合——Libratus 的蓝图压缩前是
TB 级，抽象后的蓝图动辄数百 GB。

结论：**「在本地加载一个大蓝图」这类方案整体排除**，不再作为候选。可行的只剩两类——
接口调用，或我们自己算得起的小模型 / 范围表。

## 可 API 调用的选项（2026-08-17 复核）

| 平台 | 接口 | 格式 | 强度证据 | 结论 |
|---|---|---|---|---|
| Slumbot | 免费 HTTP | 仅单挑，200bb | 2018 ACPC 冠军、近纳什；GTO Wizard AI 15 万手 19.4 bb/100 胜之 | **采用** |
| Open Poker | WebSocket | 2–6 人 | 无。bot 互殴竞技场，对手是他人所写、强度随赛季变动 | 备选陪练场，不可作标尺 |
| GTO Wizard | 无。ToS **明令禁止**系统性查询提取策略，亦禁止用其数据训练/校准第三方求解器 | — | — | **不可用（合规）** |
| Poker Scientist | 无 | 现金 / 单挑 / MTT | 自称 Nash 距离 0.01–0.15% 底池每手 | 无接口，不可用 |

**关键事实：能通过接口拿到的强对手只有单挑（Slumbot）。六人桌不存在任何 API 可调、
强度有据的 bot。**

## 决策

1. **单挑**：接 Slumbot 公开 API，既作"强对手"模式，也作外部标尺。零模型风险，需联网。
2. **六人桌**：只能自建——翻前求解范围表 + 范围跟踪 + 翻后求解。这条路**不吃内存**
   （范围表只有几 MB），真正的算力开销在翻后单点求解，限制动作树后 8 GB 显存可承受。
3. 本地大蓝图（DecisionHoldem）与 AlphaNLHoldem 均**排除**，不再花时间。

## 影响

对主线无影响：**六人桌才是主线，单挑只是强度校准场**。M1 的主交付——六人桌翻前范围表
与风格层——本来就不依赖任何外部权重。这次复核反而确认了自建是唯一可行路径。

## 教训

「公开了 checkpoint」不等于「可复用的强模型」。评估外部模型时，至少要核到：
框架与依赖是否装得起来、训练时的筹码深度与我们的场景是否一致、是否收敛、
**有没有对第三方基准的量化战绩**。最后一条最关键——没有数字的强度描述一律按"未知"处理。
